    大模型高性能算子实战：基于 Triton 实现 SwiGLU 融合算子¶

    1. SwiGLU简介¶

    SwiGLU（Swish-Gated Linear Unit） 是由 Google 团队在 2020 年的论文《GLU Variants Improve Transformer》中提出的一种高效门控激活函数。目前，它已经成为绝大多数现代主流大语言模型（如 LLaMA、Qwen、Mistral、Gemma 等）标准 MLP / FFN（前馈神经网络）层的标配，全面取代了传统的 ReLU 和 GELU。

    1.1 数学定义与公式¶

    在传统的 Transformer FFN 中，通常使用单矩阵投影加激活函数（如 GELU）：

    \text{FFN}(x) = \text{max}(0, x W_1) W_2 \quad \text{或} \quad \text{GELU}(x W_1) W_2

    而 SwiGLU 引入了 门控机制（Gating Mechanism）。它将输入通过两个不同的线性变换投影到隐空间，其中一个分支通过 Swish（即 SiLU） 激活函数作为“门（Gate）”，另一个分支作为特征内容，两者进行逐元素相乘（Element-wise Product）：

    \text{SwiGLU}(x) = \left( \text{SiLU}(x W_g) \odot (x W_k) \right) W_o

    其中：

    • W_g 和 W_k 分别是门控投影矩阵和特征投影矩阵。
    • \text{SiLU}(x) = x \cdot \sigma(x) = \frac{x}{1 + e^{-x}}（当 Swish 的 \beta=1 时即为 SiLU）。
    • \odot 表示 Hadamard 乘积（逐元素相乘）。
    • W_o 是输出投影矩阵。

    1.2 为什么 SwiGLU 能在模型效果上胜出？¶

    1. 动态信息过滤（门控特性）：门控机制赋予了网络类似 LSTM 的遗忘/选择能力。模型可以根据输入内容动态调节不同特征通道的权重，从而提升模型的表达能力。
    2. SiLU 激活函数的非单调性：SiLU 具有平滑、非单调、且在负半轴趋于零但允许微小梯度梯度的特性，相比于 ReLU 的硬截断，能够带来更好的梯度传播和模型拟合能力。
    3. 经验性验证：在相同计算成本或参数量下，SwiGLU 在语言建模任务中能够显著降低困惑度（Perplexity），展现出更强的下游任务泛化能力。

    2. 整体实现步骤¶

    2.1 计算步骤¶

    完整的SwiGLU计算包括三步：

    • 求x_1=xW_g和x_2=xW_h
    • 计算y = (x_1\sigma(x_1)) \odot x2
    • 计算yW_o

    为了优化，第一步通常用将两个权重矩阵 W_g 和 W_h在列方向（通道/隐层维度）拼接为一个大的权重矩阵 W_{\text{gate_up}}（形状为 [d, 2h]），通过 一次大的矩阵乘法 x W_{\text{gate_up}} 同时计算出 [x_1, x_2]，然后再通过切片（Split）将其分为两半。

    这样做的优势在于：

    • 减少 Kernel 启动与调度开销：将两次独立的 GEMM 合并为一次，避免了两次独立的 CUDA Kernel 启动。
    • 提高算术强度（Arithmetic Intensity）与 Tensor Core 利用率：更大的矩阵乘法尺寸能更好地饱和 GPU 的算力单元和片上缓存，减少访存瓶颈。

    所以第二步的输入是[x_1, x_2]。

    2.2 算子融合¶

    如果分成三步（两次 GEMM \rightarrow SiLU \rightarrow 逐元素乘法 \rightarrow 第三次 GEMM），会产生大量的中间激活值（Intermediate Activations），并且需要频繁地将数据在高带宽内存（HBM）和片上寄存器/SRAM 之间来回搬运。这会导致严重的 Memory-Bound（访存受限）。

    更好的方法是：通过自定义 CUDA C++ 或 Triton 算子将多个操作进行极致融合：

    1. 将 W_g 和 W_k 的矩阵乘法（GEMM）输出在 Epilogue（尾部处理阶段） 直接与 SiLU 和逐元素乘法融合进同一个 Kernel 中，减少一次 HBM 读写。
    2. 在反向传播中，需要手写高度优化的反向梯度计算 Kernel，以避免显存暴涨并最大化 Tensor Core 利用率。

    2.3 Triton 与 C++ CUTLASS 方案的深度对比¶

    在实现大模型 FFN/SwiGLU 的算子融合时，业界主要存在两条主流路线：Python + Triton 动态编译路线**与 **C++ + NVIDIA CUTLASS 模板库路线。两者的核心区别与优劣势如下表所示：

    维度 Triton 融合方案 C++ CUTLASS 融合方案
    开发语言与生态 Python 语法，JIT 实时编译，与 PyTorch 2.x 生态（如 torch.compile）天然契合。 C++ 模板编程，需配置 CUDA 编译工具链（nvcc），集成进 PyTorch 较为繁琐（Extension）。
    GEMM 性能极限 手写 MatMul 模板难以匹敌硬件厂商闭源优化，在矩阵较小时容易因指令调度劣势损失算力。 依托 NVIDIA 官方底层模板，直接调用 Tensor Core 满血指令（如 mma/wgmma 和 TMA），性能逼近物理极限。
    Epilogue 融合能力 适合做独立的逐元素激活算子融合，若要做“GEMM + 激活”的全融合，需自己实现复杂的循环分块。 通过 Epilogue Visitor 机制，可完美在满血 GEMM 的尾部注入任意自定义激活逻辑，中间结果零 HBM 读写。
    工程迭代速度 极快。几行 Python 代码即可调整 Block 尺寸、添加自动调优（autotune）并热更新。 较慢。涉及复杂的 C++ 模板实例化、编译耗时久，调试难度高。

    2.4 本课程重点关注第二步¶

    在高性能算子工程的教学与落地中，我们选择 先隔离矩阵乘法（GEMM），集中精力攻克激活算子（或 Epilogue 阶段）的 Triton 实现，主要是出于以下三个维度的教学与工程简化考量：

    1. 解耦核心矛盾，降低认知负载： 手写一个工业级的高性能矩阵乘法需要处理极其复杂的 共享内存分块（Shared Memory Tiling）、软件流水线（Software Pipelining）、双缓冲（Double Buffering）以及寄存器分配限制。如果一开始就陷入底层的 MatMul 调度陷阱，会严重分散对“算子融合本质”和“现代编译器机制”的注意力。
    2. 聚焦 Triton 的核心优势区： Triton 最强、最优雅的地方在于处理 内存密集型（Memory-Bound）的逐元素/归约操作（如激活函数、LayerNorm、RMSNorm、RoPE 等）。通过将独立激活函数（如我们的 _swiglu_forward_triton_kernel）写至极致，并配合 @triton.autotune，我们可以用极短的代码捕获到极高的访存带宽利用率。
    3. 完美无缝对接 PyTorch 生态： 将极致优化的独立 Triton 激活算子与底层由 cuBLASLt 撑腰的原生 GEMM 结合，往往能在 开发效率 和 极致性能 之间取得最佳的平衡点。

    3. 使用Pytorch的Native实现¶

    2.1 前向算法¶

    def native_swiglu_act(x):
    x1, x2 = x.chunk(2, dim=-1)
    return (x1 * torch.sigmoid(x1)) * x2

    1. x1, x2 = x.chunk(2, dim=-1)

      • 分块操作：x 是输入的张量。chunk(2, dim=-1) 表示沿最后一个维度（dim=-1，即特征维度）将其**等分成两半**，分别赋值给 x1 和 x2。
      • 例如：如果输入 x 的形状是 (Batch, 2048)，经过分块后，x1 和 x2 的形状都是 (Batch, 1024)。

    2. torch.sigmoid(x1)

      • 门控计算：对前半部分张量 x1 计算 Sigmoid 函数值。在 Swish 激活函数中，其公式为 x \cdot \text{sigmoid}(x)。

    3. x1 * torch.sigmoid(x1)

      • Swish 激活：这部分实际上就是 Swish（或称 SiLU）激活函数。它让 x1 乘以它自己的 Sigmoid 激活值，具备平滑、非单调的特性，通常比传统的 ReLU 表现更好。

    4. (x1 * torch.sigmoid(x1)) * x2

      • 门控机制（Gated Linear Unit）：将计算好的 Swish 激活结果与后半部分张量 x2 进行**逐元素相乘（Element-wise Product）**。
      • 这里的 x2 充当了“门控（Gate）”的角色，它决定了 x1 的特征中有多少可以通过并传递到下一层，从而增强了模型的表达能力。

    2.2 反向算法¶

    因为我们使用Pytorch自带的算子，所以不需要我们手写反向算法，在PyTorch里，当我们组合使用内置的高阶算子（例如 @ 矩阵乘法、torch.sigmoid、基本的算术运算符 * 和 +）时，完全不需要手动去写反向传播的数学公式和求导代码，这是因为 PyTorch 具备两项核心机制：

    1. 动态计算图（Autograd 引擎）

      • 当你在前向传播中使用 PyTorch 的原生 Tensor 和操作符时，PyTorch 会在后台自动构建一个 有向无环图（DAG，即计算图）。
      • 图中的每个节点代表一个 Tensor，边代表对 Tensor 进行的操作。

    2. 自动求导机制（Automatic Differentiation）

      • PyTorch 的每个内置算子在底层（C++ 实现中）都已经 硬编码并绑定了对应的导数计算函数（Backward Formula）。
      • 当你调用 .backward() 或在损失函数上触发反向传播时，Autograd 引擎会沿着计算图进行 反向遍历（Reverse-mode autodiff），自动应用 链式法则（Chain Rule），依次将上游梯度与各个内置算子的导数相乘，逐层向前自动计算并回传梯度。

    4. 使用torch.compile对Native版本进行优化¶

    compiled_swiglu_act = torch.compile(native_swiglu_act, mode="max-autotune")

    我们可以使用 torch.compile，对我们前面定义的原生 SwiGLU 激活函数进行了深度编译与优化。

    1. torch.compile(...)（图编译与内核融合引擎）

      • 机制：它会将普通的 Python 函数（如 native_swiglu_act）通过 TorchInductor 后端转换为优化的底层 Triton 代码或 C++/CUDA 内核。
      • 内核融合（Kernel Fusion）：在默认的 Eager 模式下，像 chunk、sigmoid、多次乘法等操作会生成多个独立的 CUDA 内核，每次运算都要把数据从显存（HBM）读到寄存器，计算完再写回显存（造成严重的“内存带宽瓶颈”）。而 torch.compile 会将这些连续的点对点操作 融合成一个单一的内核，大大减少显存读写开销。

    2. mode="max-autotune"（极致自动调优模式）

      • 作用：这是 torch.compile 中 最激进、优化程度最高 的模式。
      • 代价与收益：它在代码第一次运行（Warmup 预热阶段）时，会花费额外的时间在后台进行大量的穷举测试（Autotune），寻找最适合当前硬件架构（如最优的 Block 大小、线程束分配等）的编译配置。因此第一次运行会比较慢，但一旦编译缓存生成，后续的执行速度会达到巅峰。

    5. 使用Triton实现SwiGLU¶

    5.1 前向算法¶

    5.1.1 代码¶

    @triton.jit
def _swiglu_forward_triton_kernel(
    x_ptr, out_ptr, 
    n_elements, D,
    BLOCK_SIZE: tl.constexpr
):
    pid = tl.program_id(axis=0)
    block_start = pid * BLOCK_SIZE
    offsets = block_start + tl.arange(0, BLOCK_SIZE)
    mask = offsets < n_elements

    # 计算对应的 row 和 col
    row = offsets // D
    col = offsets % D

    # 逻辑总维度 2D
    offset_x1 = row * (2 * D) + col
    offset_x2 = offset_x1 + D

    x1 = tl.load(x_ptr + offset_x1, mask=mask)
    x2 = tl.load(x_ptr + offset_x2, mask=mask)

    # Sigmoid 计算
    sig_x1 = 1.0 / (1.0 + tl.exp(-x1))
    out = (x1 * sig_x1) * x2

    tl.store(out_ptr + offsets, out, mask=mask)

    5.1.2 代码解释¶

    5.1.2.1. 线程与块索引计算¶
    pid = tl.program_id(axis=0)
block_start = pid * BLOCK_SIZE
offsets = block_start + tl.arange(0, BLOCK_SIZE)
mask = offsets < n_elements
    • pid: 获取当前代码块（Program/Block）在一维网格中的 ID。
    • offsets: 计算当前块内每个线程负责处理的 全局一维索引（通过 BLOCK_SIZE 划分任务）。
    • mask: 边界掩码。当总元素个数不是 BLOCK_SIZE 的整数倍时，防止越界访问。
    5.1.2.2. 二维坐标映射与内存寻址¶
    row = offsets // D
col = offsets % D

offset_x1 = row * (2 * D) + col
offset_x2 = offset_x1 + D
    • 坐标转换：由于输入张量在逻辑上是二维的（形状为 [N, D] 的输出，对应 [N, 2*D] 的输入），这里通过整除和取余将一维索引 offsets 还原为矩阵的 row（行号） 和 col（列号）。
    • SwiGLU 内存布局：SwiGLU 的输入在特征维度上被等分成了两半（x1 和 x2 共占 2*D 列）。
      • offset_x1：定位前半部分 x1 的内存地址。
      • offset_x2：定位后半部分 x2 的内存地址（在 x1 的基础上向右偏移了 D 列）。
    5.1.2.3. 数据加载与计算¶
    x1 = tl.load(x_ptr + offset_x1, mask=mask)
x2 = tl.load(x_ptr + offset_x2, mask=mask)

sig_x1 = 1.0 / (1.0 + tl.exp(-x1))
out = (x1 * sig_x1) * x2
    • tl.load：根据计算好的偏移量和掩码，从全局显存（HBM）中批量加载数据到寄存器。
    • SwiGLU 计算：
      1. 计算 x1 的 Sigmoid 值：\text{sigmoid}(x_1) = \frac{1}{1 + e^{-x_1}}。
      2. 套用 SwiGLU 公式：(x_1 \cdot \text{sigmoid}(x_1)) \cdot x_2。
    5.1.2.4. 结果写回¶
    tl.store(out_ptr + offsets, out, mask=mask)
    • 将计算好的激活结果 out 批量写回到输出张量的对应全局显存位置中。

    5.2 反向算法的公式(了解即可)¶

    \text{SwiGLU}(x_1,x_2) = (x_1 \cdot \sigma(x_1)) \cdot x_2

    为了在反向传播中实现 backward，我们需要推导对 x_1 和 x_2 的偏导数：

    • 对 x_2 的偏导数：
    \frac{\partial \text{SwiGLU}}{\partial x_2} = x_1 \cdot \sigma(x_1)
    • 对 x_1 的偏导数（利用 Sigmoid 求导法则 \sigma'(x) = \sigma(x)(1 - \sigma(x))）：
    \frac{\partial \text{SwiGLU}}{\partial x_1} = x_2 \cdot \left[ \sigma(x_1) + x_1 \cdot \sigma(x_1)(1 - \sigma(x_1)) \right] = x_2 \cdot \sigma(x_1) \left[ 1 + x_1 (1 - \sigma(x_1)) \right]

    5.3 反向算法¶

    5.3.1 代码¶

    @triton.jit
def _swiglu_backward_triton_kernel(
    grad_out_ptr, x_ptr, grad_x_ptr,
    n_elements, D,
    BLOCK_SIZE: tl.constexpr
):
    pid = tl.program_id(axis=0)
    block_start = pid * BLOCK_SIZE
    offsets = block_start + tl.arange(0, BLOCK_SIZE)
    mask = offsets < n_elements

    row = offsets // D
    col = offsets % D

    offset_x1 = row * (2 * D) + col
    offset_x2 = offset_x1 + D

    x1 = tl.load(x_ptr + offset_x1, mask=mask)
    x2 = tl.load(x_ptr + offset_x2, mask=mask)
    dy = tl.load(grad_out_ptr + offsets, mask=mask)

    sig = 1.0 / (1.0 + tl.exp(-x1))
    dx1 = dy * x2 * sig * (1.0 + x1 * (1.0 - sig))
    dx2 = dy * x1 * sig

    tl.store(grad_x_ptr + offset_x1, dx1, mask=mask)
    tl.store(grad_x_ptr + offset_x2, dx2, mask=mask)

    5.3.2 代码解释¶

    5.3.2.1. 线程索引与矩阵坐标映射¶
    pid = tl.program_id(axis=0)
block_start = pid * BLOCK_SIZE
offsets = block_start + tl.arange(0, BLOCK_SIZE)
mask = offsets < n_elements

row = offsets // D
col = offsets % D

offset_x1 = row * (2 * D) + col
offset_x2 = offset_x1 + D
    • 坐标定位：与前向类似，通过一维线程偏移量 offsets 计算出当前线程负责处理的元素在矩阵中的行号 row 和列号 col。
    • 内存寻址：由于输入 x 的最后一维是合并在一起的 2*D（前半部分是 x1，后半部分是 x2），这里分别计算出 x1 和 x2 在全局显存中的物理地址偏移 offset_x1 和 offset_x2。
    5.3.2.2. 加载数据¶
    x1 = tl.load(x_ptr + offset_x1, mask=mask)
x2 = tl.load(x_ptr + offset_x2, mask=mask)
dy = tl.load(grad_out_ptr + offsets, mask=mask)
    • 从显存中批量加载前向保存的原始输入 x1、x2 以及上游回传的梯度 dy（grad_out）。
    5.3.2.3. 梯度计算（公式实现）¶
    sig = 1.0 / (1.0 + tl.exp(-x1))
dx1 = dy * x2 * sig * (1.0 + x1 * (1.0 - sig))
dx2 = dy * x1 * sig

    这里完美对应了数学导数公式：

    • 计算 Sigmoid 激活值：
    \text{sig} = \text{sigmoid}(x_1) = \frac{1}{1 + e^{-x_1}}
    • 计算对 x_1 的梯度 (dx1)： 根据乘积求导法则与 Swish 函数的导数公式：
    \frac{\partial y}{\partial x_1} = x_2 \cdot \frac{\partial f(x_1)}{\partial x_1} = x_2 \cdot \left[ \text{sigmoid}(x_1) + x_1 \cdot \text{sigmoid}(x_1)(1 - \text{sigmoid}(x_1)) \right] = x_2 \cdot \text{sig} \cdot (1 + x_1(1 - \text{sig}))

    再乘上游梯度 dy，即得到： dx1 = dy * x2 * sig * (1.0 + x1 * (1.0 - sig))

    • 计算对 x_2 的梯度 (dx2)： 由于 y = f(x_1) \cdot x_2，对 x_2 求偏导直接就是另一半 f(x_1)：
    \frac{\partial y}{\partial x_2} = f(x_1) = x_1 \cdot \text{sigmoid}(x_1)

    再乘上游梯度 dy，即得到： dx2 = dy * x1 * sig

    5.3.2.4. 梯度写回¶
    tl.store(grad_x_ptr + offset_x1, dx1, mask=mask)
tl.store(grad_x_ptr + offset_x2, dx2, mask=mask)
    • 将计算好的输入梯度 dx1 和 dx2 分别写回到梯度张量 grad_x 对应的显存位置中，供后续的优化器更新权重使用。

    5.4 算子封装¶

    5.4.1 代码¶

    class FusedSwiGLUTritonFunction(Function):
    @staticmethod
    def forward(ctx, x):
        x = x.contiguous()
        N, total_D = x.shape
        D = total_D // 2
        n_elements = N * D

        out = torch.empty((N, D), device=x.device, dtype=x.dtype)
        grid = lambda meta: (triton.cdiv(n_elements, meta['BLOCK_SIZE']),)

        _swiglu_forward_triton_kernel[grid](
            x, out, 
            n_elements, D, 
            BLOCK_SIZE=1024
        )
        ctx.save_for_backward(x)
        return out

    @staticmethod
    def backward(ctx, grad_output):
        grad_output = grad_output.contiguous()
        (x,) = ctx.saved_tensors
        N, total_D = x.shape
        D = total_D // 2
        n_elements = N * D

        grad_x = torch.empty_like(x)
        grid = lambda meta: (triton.cdiv(n_elements, meta['BLOCK_SIZE']),)

        _swiglu_backward_triton_kernel[grid](
            grad_output, x, grad_x,
            n_elements, D,
            BLOCK_SIZE=1024
        )
        return grad_x

    5.4.2 代码解释¶

    这段代码定义了一个继承自 torch.autograd.Function 的自定义自动求导类 FusedSwiGLUTritonFunction。

    它的核心作用是：将我们用 Triton 手写的前向和反向内核（Kernel）包装成一个标准的 PyTorch 算子，使其能够无缝接入 PyTorch 的计算图（Computational Graph）中，从而在神经网络训练时自动触发前向计算与反向梯度回传。

    5.4.2.1 整体架构概述¶

    在 PyTorch 中，如果使用了自定义的底层加速内核（如 Triton 或 CUDA），框架默认不知道怎么对它求导。通过继承 torch.autograd.Function 并实现静态方法 forward 和 backward，你可以手动指定：

    1. 前向时：调用哪个 Triton 前向内核，并保存哪些中间变量。
    2. 反向时：如何利用保存的变量和上游梯度，调用 Triton 反向内核计算并回传梯度。
    5.4.2.2 forward 方法解析（前向传播）¶
        @staticmethod
    def forward(ctx, x):
        x = x.contiguous()
        N, total_D = x.shape
        D = total_D // 2
        n_elements = N * D

        out = torch.empty((N, D), device=x.device, dtype=x.dtype)
        grid = lambda meta: (triton.cdiv(n_elements, meta['BLOCK_SIZE']),)

        _swiglu_forward_triton_kernel[grid](
            x, out, 
            n_elements, D, 
            BLOCK_SIZE=1024
        )
        ctx.save_for_backward(x)
        return out
    1. x = x.contiguous()：确保输入的 Tensor 在显存中是连续存储的，防止因为切片或转置导致 Triton 在寻址时发生内存越界或错误。

    2. 维度解析：

      • 获取输入形状 [N, total_D]。
      • 因为 SwiGLU 的输入在特征维被等分成了两半（x1 和 x2），所以真正的输出维度 D = total_D // 2。
      • n_elements = N * D 表示总共需要并行计算的元素个数。

    3. 显存分配与网格配置：

      • torch.empty(...) 在 GPU 上开辟一块未初始化的大空间用于存放前向输出结果 out。
      • grid 定义了 Triton 内核的启动网格（Grid Size），通过 triton.cdiv 根据总元素数和块大小（BLOCK_SIZE=1024）计算需要启动多少个线程块。

    4. 内核调用：启动前面定义好的 _swiglu_forward_triton_kernel，将输入 x 和输出指针传入 GPU 执行。

    5. ctx.save_for_backward(x)：至关重要的一步。由于反向传播计算梯度时需要用到原始输入 x（即 x1 和 x2），这里通过上下文对象 ctx 将其保存起来。
    6. return out：返回计算好的前向输出结果。
    5.4.2.3 backward 方法解析（反向传播）¶
        @staticmethod
    def backward(ctx, grad_output):
        grad_output = grad_output.contiguous()
        (x,) = ctx.saved_tensors
        N, total_D = x.shape
        D = total_D // 2
        n_elements = N * D

        grad_x = torch.empty_like(x)
        grid = lambda meta: (triton.cdiv(n_elements, meta['BLOCK_SIZE']),)

        _swiglu_backward_triton_kernel[grid](
            grad_output, x, grad_x,
            n_elements, D,
            BLOCK_SIZE=1024
        )
        return grad_x
    1. 接收上游梯度：grad_output 是从损失函数（Loss）反向传到当前激活层上游的梯度（即 \text{dy}）。同样调用 .contiguous() 保证连续性。
    2. 恢复保存的张量：通过 ctx.saved_tensors 取出在前向传播中保存的输入 x。
    3. 分配梯度显存：torch.empty_like(x) 创建一个与输入 x 形状、设备和数据类型完全相同的空 Tensor grad_x，用来存放计算出来的输入梯度。
    4. 内核调用：启动 _swiglu_backward_triton_kernel，传入上游梯度 grad_output 和原始输入 x，并行计算出 grad_x。
    5. return grad_x：将计算好的梯度返回给 PyTorch 框架，以便上一层网络继续向前推进反向传播。

    6.1 代码¶

    # ---------------------------------------------------------------------------
# 1. 编写 CUDA Kernel & C++ 接口代码
# ---------------------------------------------------------------------------
cuda_source = """
#include <torch/extension.h>
#include <cuda.h>
#include <cuda_runtime.h>

__device__ __forceinline__ float sigmoid(float x) {
    return 1.0f / (1.0f + expf(-x));
}

__global__ void swiglu_forward_kernel(
    const float* __restrict__ x, 
    float* __restrict__ out, 
    int N, int D
) {
    int idx = blockIdx.x * blockDim.x + threadIdx.x;
    if (idx < N * D) {
        int row = idx / D;
        int col = idx % D;

        int offset_x1 = row * (2 * D) + col;
        int offset_x2 = offset_x1 + D;

        float x1 = x[offset_x1];
        float x2 = x[offset_x2];

        float sig_x1 = sigmoid(x1);
        out[idx] = (x1 * sig_x1) * x2;
    }
}

__global__ void swiglu_backward_kernel(
    const float* __restrict__ grad_out, 
    const float* __restrict__ x, 
    float* __restrict__ grad_x, 
    int N, int D
) {
    int idx = blockIdx.x * blockDim.x + threadIdx.x;
    if (idx < N * D) {
        int row = idx / D;
        int col = idx % D;

        int offset_x1 = row * (2 * D) + col;
        int offset_x2 = offset_x1 + D;

        float x1 = x[offset_x1];
        float x2 = x[offset_x2];
        float dy = grad_out[idx];

        float sig = sigmoid(x1);
        float dx1 = dy * x2 * sig * (1.0f + x1 * (1.0f - sig));
        float dx2 = dy * x1 * sig;

        grad_x[offset_x1] = dx1;
        grad_x[offset_x2] = dx2;
    }
}

at::Tensor swiglu_forward_cuda(at::Tensor x) {
    TORCH_CHECK(x.is_cuda(), "x 必须是 CUDA tensor");
    TORCH_CHECK(x.dim() == 2, "输入必须是 2D 矩阵 [N, 2D]");

    int N = x.size(0);
    int total_D = x.size(1);
    TORCH_CHECK(total_D % 2 == 0, "输入维度必须能被 2 整除");
    int D = total_D / 2;

    auto out = torch::empty({N, D}, x.options());

    int threads = 256;
    int blocks = (N * D + threads - 1) / threads;

    swiglu_forward_kernel<<<blocks, threads>>>(
        x.data_ptr<float>(),
        out.data_ptr<float>(),
        N, D
    );
    return out;
}

at::Tensor swiglu_backward_cuda(at::Tensor grad_out, at::Tensor x) {
    int N = x.size(0);
    int D = x.size(1) / 2;

    auto grad_x = torch::empty_like(x);

    int threads = 256;
    int blocks = (N * D + threads - 1) / threads;

    swiglu_backward_kernel<<<blocks, threads>>>(
        grad_out.data_ptr<float>(),
        x.data_ptr<float>(),
        grad_x.data_ptr<float>(),
        N, D
    );
    return grad_x;
}
"""

cpp_decl = """

at::Tensor swiglu_backward_cuda(at::Tensor grad_out, at::Tensor x);
"""

    6.2 代码解释¶

    这段代码通过 PyTorch 的 torch.utils.cpp_extension.load_inline 工具，实现了在 Python 中 动态编译并加载手写的 C++ / CUDA 扩展算子。

    它由 CUDA 内核实现（GPU 并行计算） 和 C++ 胶水接口（Python 与 GPU 的桥梁） 两部分组成。

    6.2.1 CUDA 内核部分¶

    这部分是用 CUDA C++ 编写的底层硬件加速代码，运行在显卡的各个线程上。

    1. sigmoid 辅助函数
    __device__ __forceinline__ float sigmoid(float x) {
    return 1.0f / (1.0f + expf(-x));
}

    * __device__ 表示该函数只能在 GPU 上的设备端（Device）被调用。 * __forceinline__ 建议编译器尽可能将其内联展开，减少函数调用的开销，提升执行效率。

    1. swiglu_forward_kernel（前向传播内核）

      • 并行映射：每个线程通过 int idx = blockIdx.x * blockDim.x + threadIdx.x; 获取自己的全局唯一线程 ID，负责计算输出矩阵中的一个元素。
      • 索引计算：输入矩阵 x 的形状是 [N, 2D]（最后一维被等分成了两半），输出形状是 [N, D]。通过行号和列号计算出 x1 和 x2 在一维大数组中的具体内存偏移量 (offset_x1, offset_x2)。
      • 核心计算：加载 x1 和 x2，计算 x_1 \cdot \text{sigmoid}(x_1) \cdot x_2，并将结果存入输出显存。

    2. swiglu_backward_kernel（反向传播内核）

      • 根据我们在前面介绍的数学公式，利用上游传下来的梯度 grad_out（即 \text{dy}）以及保存的输入 x1, x2，并行计算出对输入的梯度 dx1 和 dx2，并写回到 grad_x 的对应位置。

    6.2.2 C++ 胶水接口部分（Python 胶水层）¶

    这部分负责接收来自 PyTorch 的 Tensor，进行安全性检查，并负责将任务分发给上面的 CUDA 内核。

    1. swiglu_forward_cuda 函数

      • 安全检查：TORCH_CHECK 确保输入的张量必须在 GPU 上（.is_cuda()）、必须是 2D 矩阵，并且特征维度能被 2 整除。
      • 分配显存：auto out = torch::empty({N, D}, x.options()); 在 GPU 上开辟一块用于存放输出结果的显存。
      • 配置线程网格（Grid & Block）： 
        int threads = 256;
int blocks = (N * D + threads - 1) / threads;
        设定每个 Thread Block 包含 256 个线程，并根据总计算元素个数 N * D 向上取整计算需要多少个 Block。
      • 调用 Kernel：swiglu_forward_kernel<<<blocks, threads>>>(...) 语法启动 GPU 内核。

    2. swiglu_backward_cuda 函数

      • 类似的逻辑，负责接收 grad_out 和保存的 x，开辟 grad_x 显存，并启动反向传播的 CUDA 内核。

    7.2 性能与加速比分析¶

    1. PyTorch 原生组合 (Eager)         耗时 : 2.431 ms  (基准 1.00x)
2. 手写 C++/CUDA 融合 Kernel        耗时 : 1.190 ms  (加速 2.04x)
3. 手写 Triton 融合 Kernel          耗时 : 1.180 ms  (加速 2.06x)
4. 原生组合 + torch.compile (Triton) 耗时 : 1.388 ms  (加速 1.75x)

    1. 为什么优化后能实现 ~2x 的加速？¶

    SwiGLU 是一个典型的 “内存带宽受限型（Memory-Bound）” 算子。

    • 原生 PyTorch（Eager 模式）：会把整个过程拆分成多个独立的步骤（chunk \to sigmoid \to 乘法 \to 乘法），每一步都要把中间结果从显存（HBM）读出来、计算、再写回显存。这造成了严重的 显存带宽浪费。
    • 融合内核（Kernel Fusion）：手写的 CUDA 和 Triton 将所有操作融合成一个内核，数据只需从显存读一次，在寄存器里一口气算完前向（或反向），然后直接写回显存。省去了大量中间显存读写开销，因此实现了 ~2.05 倍的显著加速。

    2. 三种优化方案的横向对比¶

    • 手写 Triton (1.180 ms) vs 手写 C++/CUDA (1.190 ms)：
      • 两者性能几乎完全一致（Triton 甚至略微快一点点）。
      • 这证明了 Triton 的高维抽象能力 已经能够达到甚至媲美底层手写低级 CUDA 代码的性能，但其开发效率和代码可读性远高于 C++/CUDA。
    • torch.compile (1.388 ms, 1.75x)：
      • 虽然比手写内核稍慢一点，但它 完全不需要写任何底层 Kernel 代码，仅仅通过一行 torch.compile 就自动完成了图融合，拿到了 1.75x 的加速。
      • 它是性价比最高的优化方案，适合不想维护自定义内核但又想吃满硬件优化的场景。
