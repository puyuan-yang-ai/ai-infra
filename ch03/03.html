    Fused Softmax¶

    学习目标¶

    • 理解内核融合的作用

    1. Naive的softmax¶

    首先我们用Pytorch实现最简单的Softmax作为baseline。这里我们假设Pytorch没有提供一个softmax函数，所以我们用其它基本函数来实现它。

    def naive_softmax(x):
    """使用原生 PyTorch 计算 X 的行级 softmax

    我们减去最大元素以避免溢出。Softmax 对这种平移是不变的。
    """
    # 读取 MN 个元素；写入 M 个元素
    x_max = x.max(dim=1)[0]
    # 读取 MN + M 个元素；写入 MN 个元素
    z = x - x_max[:, None]
    # 读取 MN 个元素；写入 MN 个元素
    numerator = torch.exp(z)
    # 读取 MN 个元素；写入 M 个元素
    denominator = numerator.sum(dim=1)
    # 读取 MN + M 个元素；写入 MN 个元素
    ret = numerator / denominator[:, None]
    # 总计：读取 5MN + 2M 个元素；写入 3MN + 2M 个元素
    return ret

    1.1 torch.max¶

    1.1.1 它的返回值¶

    如果不熟悉Pytorch的同学可能会奇怪：x.max(dim=1)[0]为什么取下标是0的元素？

    在 PyTorch 中，当对一个张量调用 x.max(dim=1) 时，它返回的不是一个单一的张量，而是一个包含 两个张量的元组 (tuple)：(values, indices)。

    • [0] (values)：沿指定维度（这里是 dim=1，即每一行）找出的 最大值。
    • [1] (indices)：这些最大值在对应行中所在的 索引位置。

    在计算 Softmax 时，我们需要用每一行的实际数值去减去该行的最大值（为了防止指数运算溢出），因此只需要用到最大值本身，所以通过 [0] 取出最大值张量，而丢弃位置索引。

    1.1.2 为什么要这么设计¶

    1.1.2.1. 硬件与内存层面：单次访存（Single-Pass），几乎零额外开销¶

    在 GPU 计算中，类似 max 这种规约（Reduction）操作，最大的瓶颈往往不是计算能力，而是 显存带宽（Memory-bound）。

    • 当 GPU 读取显存中的张量数据时，顺便在寄存器或共享内存中维护两个变量（一个记 max_val，一个记 max_idx）只增加了一个极低开销的比较指令。
    • 如果把它们拆开——让用户先调用一个算子求最大值，再调用另一个算子求下标——GPU 就需要把同一块显存数据 读取两次，并启动两个不同的 Kernel。这会浪费大量的显存带宽和调度时间。
    • 因此，“顺手”把下标带上，是用最低的计算代价换取了最高效的内存利用率。
    1.1.2.2. 深度学习反向传播（Autograd）的刚需¶

    在 PyTorch 中，许多操作不仅要管前向（Forward），还要支持反向求导（Backward）。

    • 以 max 运算或最大池化（Max Pooling）为例，在前向传播时选出了最大值；在反向传播时，梯度必须准确无误地回传给当初贡献这个最大值的那个输入元素。
    • 如果不返回下标，框架在反向传播时根本无法知道梯度该给谁，必须重新计算一遍或做额外存储。返回下标为自动微分提供了直接的依据。
    1.1.2.3. 业务场景的高频刚需¶

    在实际的 AI 开发中，我们几乎很少只想要最大值而完全不关心它的位置：

    • 分类任务：torch.max(logits, dim=-1) 既需要预测的概率值（置信度），又需要对应的类别索引（Class ID）。
    • 目标检测 / NMS：需要最高得分及其对应的锚框/候选框下标。
    • 文本生成 / 采样：需要知道最大概率的 Token ID 是哪个。

    如果只返回一个值，开发者在 90% 的场景下还要去多调用一次 argmax，这既降低了代码效率，又增加了 Kernel 调度的开销。

    1.1.2.4 总结¶

    这种“买一赠一”的设计，在底层只需多消耗几个寄存器，却省掉了一次昂贵的显存重复读取，同时满足了反向传播和上层业务的痛点。它是深度学习框架中兼顾 性能 与 易用性 的经典工程优化。

    1.1.3 如果我只需要其中之一呢？¶

    如果你的业务场景极其纯粹，“只需要最大值（不要下标）” 或 “只需要下标（不要最大值）”，PyTorch 也提供了对应的专用 API 来避免多余的内存占用和后续处理：

    1.1.3.1. 只需要最大值¶

    可以直接使用 torch.amax()，或者在调用 torch.max() 后丢弃第二个返回值：

    • torch.amax(input, dim)： 专为规约求最大值设计，它 只返回最大值本身，不计算也不返回下标。在某些特定的分布式或图优化场景下，它能让编译器做更好的算子融合。
    • 直接解包或切片丢弃： 
      max_val = torch.max(x, dim=-1).values
# 或者
max_val, _ = torch.max(x, dim=-1)
    1.1.3.2. 只需要下标¶

    可以直接使用 torch.argmax()：

    • torch.argmax(input, dim)： 它 只返回对应的下标索引，不返回最大值。语义上更加清晰，代码可读性更高。
    import torch

x = torch.tensor([[1.0, 5.0, 3.0], [4.0, 2.0, 6.0]])

# 只需要最大值
vals = torch.amax(x, dim=-1) # tensor([5., 6.])

# 只需要下标
indices = torch.argmax(x, dim=-1) # tensor([1, 2])
    1.1.3.3 总结¶
    • 如果只要 值，用 torch.amax()。
    • 如果只要 下标，用 torch.argmax()。
    • 如果 两者都要（分类、检索常用），用 torch.max() 一次拿完，最高效。

    torch.max 和 torch.maximum 虽然名字很像，但它们在 核心功能、输入支持以及计算逻辑 上有本质的区别。

    1. torch.max() 的用法¶
    • 用法一：规约求最大值（最常用） 沿着指定维度（dim）寻找最大值，会同时返回 最大值 和 对应的下标。
    import torch

x = torch.tensor([[1.0, 5.0], [4.0, 2.0]])
# 沿 dim=1 求最大值
vals, indices = torch.max(x, dim=1)
print(vals)  # tensor([5., 4.])
print(indices)  # tensor([1, 0])
    • 用法二：双张量逐元素比较（与 torch.maximum 类似）

    当传入两个张量时，它会逐元素对比并取较大者（但不支持像 torch.maximum 那样平滑地处理某些特定广播或类型转换，通常推荐用 torch.maximum）。

    2. torch.maximum() 的用法¶
    • 逐元素求最大值（Element-wise Max） 它对两个形状相同（或可广播）的张量进行 位置一一对应 的比较，取各自位置上的较大值，不改变张量的形状，也没有下标返回。
    import torch

a = torch.tensor([1.0, 5.0, 3.0])
b = torch.tensor([2.0, 3.0, 4.0])

# 逐元素对比：max(1, 2), max(5, 3), max(3, 4)
result = torch.maximum(a, b)
print(result)  # tensor([2., 5., 4.])

    常见应用场景：实现 ReLU 激活函数的变体（如 torch.maximum(x, 0) 相当于 relu 的一部分），或者将张量裁剪到某个下限。

    1.1.4.3. 总结：怎么选？¶
    • 如果你想 在一个维度上压缩张量，顺便找最大值在哪（比如分类、排序、池化），用 torch.max(x, dim=...)。
    • 如果你想 按位置对比两个张量，保留原有形状，取每个位置的较大者（比如矩阵对应位置截断、多路信号取峰值），用 torch.maximum(a, b)。

    1.2 x_max[:, None]的作用¶

    因为x.max(dim=1)[0]得到的是长度为M的向量(而不是(M,1)的矩阵)，所以为了能够广播相减，先给它增加一个维度。

    其实x.max() 还有 一个keepdim 参数。

    在 PyTorch 中，如果你调用 x.max(dim=1, keepdim=True)[0]，返回的最大值张量形状会保持为 (M, 1)，而不是降维成 (M,)。

    代码中使用 x_max = x.max(dim=1)[0]（降维成 (M,)）再加上 [:, None]（或 [:, None] 的等价写法 unsqueeze(1)），是为了把形状手动调整为 (M, 1)。

    对比

    1. 原代码写法（先降维，再手动升维广播）： 

      x_max = x.max(dim=1)[0]       # 形状是 (M,)
z = x - x_max[:, None]        # x_max[:, None] 形状变成 (M, 1)，与 (M, N) 的 x 进行广播相减

    2. 使用 keepdim=True 的等价写法（一步到位）： 

      x_max = x.max(dim=1, keepdim=True)[0]  # 形状直接就是 (M, 1)
z = x - x_max                          # 直接广播相减

    1.3 Naive实现的问题¶

    当在 PyTorch 中以朴素的方式实现时，对于 x \in R^{M \times N}，计算 y = naive_softmax(x) 需要从 DRAM 读取 5MN + 2M 个元素，并写回 3MN + 2M 个元素。

    这显然是一种浪费；我们更倾向于拥有一个自定义的“融合”内核，它只读取一次 X 并在芯片上（on-chip）完成所有必要的计算。

    这样做只需要读取和写回相对极少的数据（总读写量相当于精简到 MN 级别），因此我们可以期望获得大约 4 倍的理论加速比（即 \frac{8MN + 4M}{2MN}）。

    torch.jit.script 旨在自动执行这种“内核融合”，但正如我们稍后将看到的，它距离理想状态还相去甚远。

    2. 算子融合¶

    算子融合(Kernel Fusion)是深度学习编译和高性能计算（HPC）中最核心的优化技术之一。

    简单来说，Kernel Fusion 就是将多个连续的、独立的底层计算算子（Kernel）合并为一个单一的复合算子。

    通过这种合并，原本需要多次读写显存的中间结果直接在寄存器或片上共享内存（SRAM）中流转，从而大幅减少显存访存开销，提升 GPU 的整体计算效率。

    2.1. 为什么需要 Kernel Fusion？¶

    在理解融合之前，先看看传统“未融合”模式下的低效之处。

    假设我们要实现一个常见的神经网络操作组合：y = \text{ReLU}(Ax + b)（即矩阵乘法 + 偏置相加 + 激活函数）。 在没有算子融合的传统框架（如传统的 PyTorch 动态图分步执行）中，计算过程如下：

    1. Kernel 1 (MatMul)：从显存（Global Memory）读取矩阵 A 和 x，计算乘法，将中间结果 写回显存。
    2. Kernel 2 (Add)：从显存读取上一步的中间结果和偏置 b，相加后，再次把中间结果 写回显存。
    3. Kernel 3 (ReLU)：从显存读取上一步的中间结果，应用 ReLU，最后把最终结果 写回显存。

    核心瓶颈：内存墙（Memory Wall）

    现代 GPU 的 计算能力（FLOPs） 增长速度远快于 显存带宽（Memory Bandwidth） 的增长速度。上面这个过程中，虽然计算量很小，但 中间结果被反复写入又读出显存了 2 次。GPU 大量的时间都花在了“等待数据在显存和计算单元之间搬运”上，这就是典型的 Memory-bound（访存受限） 场景。计算单元（ALU）经常处于“饥饿”状态。

    2.2. Kernel Fusion 是如何解决这个问题的？¶

    如果采用 Kernel Fusion，编译器或开发者会将上述三个操作写成一个单一的联合 Kernel（或者通过编译器自动优化组合）：

    • 寄存器/片上缓存中传递：当 GPU 从显存加载 A 和 x 计算出矩阵乘法的某个 Tile（分块）结果后，并不急着写回显存，而是直接把它留在寄存器（Register）或共享内存（Shared Memory）中。
    • 流水线式计算：紧接着在寄存器中直接加上 b，然后立刻过一遍 ReLU 函数，最后一步到位，只把最终结果写回显存一次。

    带来的优势：

    1. 大幅减少显存读写：中间变量的显存 IO 次数从 N 次降为 0 次。
    2. 消除 Kernel 启动开销：GPU 每次启动一个 Kernel 都有一定的硬件调度延迟（Launch Overhead），合并成一个 Kernel 后只启动一次。
    3. 提升算力利用率：让 GPU 的计算单元有持续不断的数据喂养，将瓶颈从“访存受限”转化为“计算受限”。

    2.3. 典型应用场景¶

    Kernel Fusion 在大模型（LLM）和现代深度学习推理/训练中无处不在，最经典的例子包括：

    • Bias-Add + Activation 融合：如 FusedGeLU、FusedSiLU，将线性层的输出、偏置和激活函数合而为一。
    • LayerNorm / RMSNorm 融合：归一化涉及求均值、求方差、减均值、除以标准差、乘以缩放系数等多步统计和缩放操作，必须高度融合才能达到高性能。
    • FlashAttention：Transformer 中 Attention 的核心优化。它将注意力矩阵的计算（QK^T）、Softmax 归一化和与 V 的相乘（softmax \cdot V）在 SRAM 中进行分块在线融合（Online Softmax），避免了存储巨大的 N \times N 注意力权重矩阵到显存中。

    2.4. 常见的实现方式¶

    在实际工程中，Kernel Fusion 可以通过以下几种途径实现：

    1. 手写 CUDA / Triton 算子： 开发者直接使用 CUDA C++ 或 Triton 语言，把多个数学逻辑写在同一个 Kernel 函数里（例如在 Triton 中一个 Block 内连续完成 Load -> 矩阵乘 -> 激活 -> Store）。
    2. 编译器自动图优化（Graph Compiler）： 深度学习编译器（如 TensorRT、TVM、OpenXLA、PyTorch 2.x 的 torch.compile / Inductor）会自动分析计算图（Computation Graph），识别出可以合并的相邻算子，并自动生成融合后的高性能底层代码。

    3. 实现算子融合的softmax_kernel¶

    3.1 代码¶

    @triton.jit
def softmax_kernel(output_ptr, input_ptr, input_row_stride, output_row_stride, n_rows, n_cols, BLOCK_SIZE: tl.constexpr,
                   num_stages: tl.constexpr):
    # 程序的起始行
    row_start = tl.program_id(0)
    row_step = tl.num_programs(0)
    for row_idx in tl.range(row_start, n_rows, row_step, num_stages=num_stages):
        # 步幅（stride）表示我们需要将指针增加多少来前进 1 行
        row_start_ptr = input_ptr + row_idx * input_row_stride
        # 块大小是大于 n_cols 的最小 2 的幂次方，因此我们可以将每行放入单个块中
        col_offsets = tl.arange(0, BLOCK_SIZE)
        input_ptrs = row_start_ptr + col_offsets
        # 将行加载到 SRAM 中，由于 BLOCK_SIZE 可能大于 n_cols，因此使用掩码
        mask = col_offsets < n_cols
        row = tl.load(input_ptrs, mask=mask, other=-float('inf'))
        # 减去最大值以保证数值稳定性
        row_minus_max = row - tl.max(row, axis=0)
        # 请注意，Triton 中的指数运算很快但只能得到近似的计算（即类似于 CUDA 中的 __expf）
        numerator = tl.exp(row_minus_max)
        denominator = tl.sum(numerator, axis=0)
        softmax_output = numerator / denominator
        # 将输出写回 DRAM
        output_row_start_ptr = output_ptr + row_idx * output_row_stride
        output_ptrs = output_row_start_ptr + col_offsets
        tl.store(output_ptrs, softmax_output, mask=mask)

    3.2 代码解读¶

    这个内核工作原理如下：每个程序以程序数量为步长加载输入矩阵 X 的一组行，对其进行归一化，并将结果写回输出 Y。

    请注意，Triton 的一个重要限制是每个block处理的数据的大小（BLOCK_SIZE）是2的幂次方，因此如果我们想要处理任意可能的输入形状，就必须在内部对每一行进行“填充（pad）”，并妥善保护内存操作。

    注意：BLOCK_SIZE是每个线程块(block)处理数据的大小，不是这个线程块的线程数。前面讲过，线程数由Triton自动根据BLOCK_SIZE等参数决定。我们不用关心线程的个数，如果线程小于BLOCK_SIZE，那么Triton会自动在底层生成* 循环或向量化指令*。

    3.2.1 跨步循环¶

        # 程序的起始行
    row_start = tl.program_id(0)
    row_step = tl.num_programs(0)
    • tl.program_id(axis=0)（编号）： 它用来回答每一个正在运行的内核实例：我是第几个 Block？。例如，如果网格（Grid）大小为 32，那么正在并行运行的各个程序会分别从 tl.program_id(0) 拿到 0, 1, 2, ..., 31 其中的一个编号。
    • tl.num_programs(axis=0)（总数）： 它用来获取总共有多少个 Block 在并行运行（对应 CUDA 的 gridDim.x）。
    • 与“线程数”或块大小的关系： 真正决定一个 Block 内部处理多少个数据、隐式包含多少个线程规模的是 BLOCK_SIZE（在代码中通过 tl.arange(0, BLOCK_SIZE) 展开）。

    比如总共有n_rows=2048行，并且tl.program_id(0)=1，tl.num_programs(0)=128。则说明当前程序(块)的id是1(第二个块)，总共有128个程序(块)，则当前程序处理第1行、第129(1+128)行、第257行(1+128+128)、...。

    接下来就是每个程序进行跨步循环：

        for row_idx in tl.range(row_start, n_rows, row_step, num_stages=num_stages):

    3.2.2 num_stages¶

    num_stages 是 Triton 中用于控制软件流水线（Software Pipelining）的核心编译参数。关于软件流水线，后面还会详细解释，这里简单说明一下。

    因为要传入num_stages，所以这里要使用tl.range，而不是python语言里的range。

    它的主要作用是 隐藏访存延迟（Memory Latency Hidden），通过重叠“内存加载”和“数据计算”来提升 GPU 的执行效率。

    3.2.2.1. 为什么要用软件流水线？¶

    在 GPU 上，从全局显存（DRAM）读取数据是一个相对较慢的过程。如果在代码中按部就班地执行：

    1. 加载 当前行数据（耗时，计算单元空闲等待）
    2. 计算 当前行（Softmax、指数等）
    3. 写回 结果

    那么计算单元（ALU）会有大量的时间花在“等数据从显存运过来”上（即 访存受限 / Memory-Bound 导致的性能瓶颈）。

    3.2.2.2. num_stages 是怎么工作的？¶

    当设置 num_stages=4（或代码中的动态判断）时，Triton 编译器会把循环变成类似工厂的 流水线作业：

    • 当 GPU 正在 计算 第 N 行的数据时，硬件已经在后台 提前加载 第 N+1 行甚至 N+2 行的数据到 SRAM 中了。
    • 这样，当计算完第 N 行时，第 N+1 行的数据已经就绪，计算单元几乎不需要停下来等待内存。

    可以将它类比为工厂流水线：工人（计算单元）在组装当前的产品时，运输队（内存加载）已经在源源不断地把下一批零件运到工位旁，而不是等用完了再去仓库拿。

    3.2.2.3. 优缺点与权衡¶
    • 优点：能够极大地提升带宽利用率，加速类似 Softmax 这种访存密集型（Bandwidth-bound）算子的执行。
    • 代价：开启多级流水线（如 num_stages=4）需要占用更多的 共享内存（SRAM） 或 寄存器 来暂存预取的数据。如果显存开销过大，会导致 GPU 上同时运行的程序块（Block）数量减少（降低占用率 Occupancy），因此编译器和框架通常会根据硬件实际资源（如代码中的 SIZE_SMEM > 200000）来动态选择合适的级数。

    3.2.3 跨步循环内部代码¶

    3.2.3.1. 输入内存寻址 (Pointer Arithmetic)¶
    row_start_ptr = input_ptr + row_idx * input_row_stride
col_offsets = tl.arange(0, BLOCK_SIZE)
input_ptrs = row_start_ptr + col_offsets
    • row_start_ptr：计算当前处理的第 row_idx 行在全局内存（DRAM）中的起始物理地址。input_row_stride 是每一行在内存中占用的总跨度（可能包含对齐填充）。
    • col_offsets：利用 tl.arange 生成一个包含从 0 到 BLOCK_SIZE - 1 的一维索引向量。这是 Triton 实现 SIMD/SIMT 并行计算的基础。
    • input_ptrs：通过基地址加上列偏移量，广播生成当前块中 所有列元素的精确内存指针向量。

    注意：input_row_stride可能大于输入矩阵的列数n_cols，因为有可能会有padding。

    3.2.3.2. 掩码与安全加载 (Masking & Loading)¶
    mask = col_offsets < n_cols
row = tl.load(input_ptrs, mask=mask, other=-float('inf'))
    • mask：由于 Triton 要求 BLOCK_SIZE 通常必须是 2 的幂次方（以便硬件高效处理），而实际的矩阵列数 n_cols 往往不是（例如 n_cols = 1000，而 BLOCK_SIZE = 1024）。该布尔掩码用于标记哪些列是真实有效的数据。
    • tl.load：将数据从全局内存（DRAM）加载到片上高速存储（SRAM/寄存器）中。
    • other=-float('inf')：对于超出实际列数 n_cols 的越界位置（即 mask 为 False 的地方），用负无穷填补。这在 Softmax 计算中是一个精妙的设计：后续求指数时，e^{-\infty} = 0，这样填充项在求和（分母）时贡献为 0，且不会干扰最大值的计算。
    3.2.3.3. 数值稳定性与 Softmax 核心计算¶
    row_minus_max = row - tl.max(row, axis=0)
numerator = tl.exp(row_minus_max)
denominator = tl.sum(numerator, axis=0)
softmax_output = numerator / denominator
    • row_minus_max：计算当前行的最大值 tl.max(row, axis=0) 并从原数据中减去。这是标准的 Softmax 数值稳定化技巧（Log-Sum-Exp 技巧），能有效防止指数运算时因数值过大而导致的浮点数上溢（Overflow）。
    • numerator（分子）：对减去最大值后的张量执行指数运算。注释中提到 Triton 中的 tl.exp 速度极快但属于 近似计算（类似于 CUDA 的硬件指令 __expf），在追求极致性能的深度学习场景中非常实用。
    • denominator（分母）：对整行的指数结果进行求和（tl.sum），得到归一化分母。
    • softmax_output：将分子向量除以分母标量，得到最终的 Softmax 概率分布。
    3.2.3.4. 输出写回 (Storing Results)¶
    output_row_start_ptr = output_ptr + row_idx * output_row_stride
output_ptrs = output_row_start_ptr + col_offsets
tl.store(output_ptrs, softmax_output, mask=mask)
    • output_row_start_ptr 与 output_ptrs：计算输出张量中对应行的存储起始地址及块内每个元素的精确目标指针，逻辑与输入的寻址方式完全对称。
    • tl.store：带着同样的 mask，将计算好的 softmax_output 安全地写回全局内存（DRAM）中，自动过滤掉越界的填充位置，确保不会污染相邻的内存数据。

    4. 获取GPU(SM)的信息¶

    properties = driver.active.utils.get_device_properties(DEVICE.index)
NUM_SM = properties["multiprocessor_count"]
NUM_REGS = properties["max_num_regs"]
SIZE_SMEM = properties["max_shared_mem"]
WARP_SIZE = properties["warpSize"]
target = triton.runtime.driver.active.get_current_target()
kernels = {}

    这段代码用于 获取当前运行 Triton 内核的 GPU 硬件底层属性与编译目标，为后续的自动调优（Autotuning）或内核动态编译做准备。

    4.1. 获取 GPU 硬件属性 (driver.active.utils.get_device_properties(...))¶

    properties = driver.active.utils.get_device_properties(DEVICE.index)
    • 通过 Triton 的驱动模块获取指定设备索引（DEVICE.index，通常是当前正在使用的 GPU 编号，如 0）的底层硬件规格参数，返回一个包含各项硬件指标的字典 properties。

    4.2. 读取关键硬件指标¶

    • NUM_SM = properties["multiprocessor_count"]
      • 流多处理器数量（Streaming Multiprocessors）。代表 GPU 上并行计算核心群的数量。例如在 NVIDIA A100 上通常为 108。该值常用于计算网格大小（Grid Size）或评估并行负载。
    • NUM_REGS = properties["max_num_regs"]
      • 每个 SM 可用的最大寄存器数量。寄存器是 GPU 上速度最快的存储介质。如果内核代码使用的寄存器过多（Register Pressure），会导致寄存器溢出（Spill），从而拖慢性能。
    • SIZE_SMEM = properties["max_shared_mem"]
      • 每个 SM（或每个块）的最大共享内存大小（Shared Memory），通常以字节（Bytes）为单位。这决定了内核中能开辟多大的 tl.shared 或使用多大的块（BLOCK_SIZE）。
    • WARP_SIZE = properties["warpSize"]
      • Warp 大小。在 NVIDIA GPU 上，线程束（Warp）通常包含 32 个线程，所有线程以 SIMT 方式同步执行。这个值用于处理线程束级别的归约或对齐计算。

    4.3. 获取当前编译目标 (triton.runtime.driver.active.get_current_target())¶

    target = triton.runtime.driver.active.get_current_target()
    • 获取当前的 编译目标架构（如 NVIDIA 的 cuda:ampere、cuda:hopper 或 AMD 的 hip 架构以及对应的计算能力架构版本号）。Triton 编译器需要知道这个目标，以便生成对应硬件架构的 PTX 或 AMDASM 汇编代码。

    4.4. 初始化内核缓存字典¶

    kernels = {}
    • 创建一个空字典，用于 缓存编译好的 Triton 内核（Kernel）。在动态编译或根据不同参数进行 JIT 调优的场景中，将编译好的内核实例存入字典可以避免重复编译带来的性能开销。

    5. softmax函数¶

    这个函数是 Triton 中标准的 Host 端包装函数（Launcher），负责在调用底层 GPU 内核之前完成参数准备、硬件资源评估、寄存器占用率（Occupancy）计算，并最终调度和启动内核。

    5.1. 初始化配置与参数准备¶

    n_rows, n_cols = x.shape
BLOCK_SIZE = triton.next_power_of_2(n_cols)
num_warps = 8
num_stages = 4 if SIZE_SMEM > 200000 else 2
y = torch.empty_like(x)
    • BLOCK_SIZE：利用 triton.next_power_of_2(n_cols) 将实际的列数向上对齐到最近的 2 的幂次方。这是 Triton 硬件访存和向量化计算的要求。
    • num_warps = 8：指定为每一行分配 8 个 Warp（共 8 \times 32 = 256 个线程）来并发处理，以获得足够的并行度。
    • num_stages：软件流水线（Software Pipelining）级数。如果 GPU 的共享内存（SMEM）大于 200KB（如 A100/H100），则设为 4 级以更好地隐藏访存延迟；否则设为 2 级以节省内存。
    • y：在 PyTorch 中分配一块与输入形状相同的空张量用来存放输出结果。

    5.2. 内核预热与静态分析 (warmup)¶

    kernel = softmax_kernel.warmup(y, x, x.stride(0), y.stride(0), n_rows, n_cols, 
        BLOCK_SIZE=BLOCK_SIZE, num_stages=num_stages, num_warps=num_warps, grid=(1, ))
kernel._init_handles()
n_regs = kernel.n_regs
size_smem = kernel.metadata.shared
    • warmup：不真正提交到 GPU 执行，而是让 Triton 编译器提前编译内核。
    • 获取编译元数据：
      • n_regs：该内核实际编译消耗的 寄存器数量。
      • size_smem：该内核实际消耗的 共享内存大小（字节）。

    5.3. 计算 GPU 硬件占用率 (Occupancy)¶

    Occupancy（占用率）指每个 SM 上实际活跃的线程束/线程块数量占硬件极限的比例，这是决定 GPU 利用率高低的关键指标。

    5.3.1. AMD (HIP) 架构的占用率计算¶

    if is_hip():
    NUM_GPRS = NUM_REGS
    if is_cdna():
        NUM_GPRS = NUM_REGS * 2
    MAX_NUM_THREADS = properties["max_threads_per_sm"]
    max_num_waves = MAX_NUM_THREADS // WARP_SIZE
    occupancy = min(NUM_GPRS // WARP_SIZE // n_regs, max_num_waves) // num_warps
    • 针对 AMD CDNA 等架构，计算可用通用寄存器池（NUM_GPRS）和每个 CU（Compute Unit，相当于 SM）的最大 Wave 数，从而推导出受寄存器和线程数限制的单 SM 最大块数。

    5.3.2. NVIDIA 架构的占用率计算¶

    else:
    occupancy = NUM_REGS // (n_regs * WARP_SIZE * num_warps)
occupancy = min(occupancy, SIZE_SMEM // size_smem)
    • 寄存器限制：每个 SM 总寄存器数（NUM_REGS）除以单个 Block 消耗的寄存器总数（n_regs * WARP_SIZE * num_warps）。
    • 共享内存限制：取寄存器占用率与共享内存占用率（SIZE_SMEM // size_smem）两者中的 较小值，因为硬件资源是木桶效应，哪个先耗尽就受限于哪个。

    注意：n_regs 和 size_smem 在粒度上有所不同：

    • n_regs 是单线程的：它表示 单个线程 在运行该内核时所消耗的寄存器数量。 GPU 上的寄存器资源是以线程为单位独立分配的。
    • size_smem 是整个线程块（Program）的：它表示整个线程块（Block）总共消耗的共享内存大小（以字节为单位），而不是单个线程的。同一个块内的所有线程共享这块内存。

    5.3.4. 动态确定网格大小 (num_programs)¶

    num_programs = NUM_SM * occupancy
num_programs = min(num_programs, n_rows)
    • NUM_SM * occupancy：计算出当前 GPU 在考虑了寄存器和共享内存瓶颈后，整个芯片最多可以同时并行运行多少个程序块（Program Block）。
    • min(num_programs, n_rows)：如果矩阵的行数 n_rows 比硬件最大并发能力还要少，就没有必要启动那么多程序块，直接把 num_programs 限制为 n_rows，避免资源浪费。

    5.3.5. 启动内核与返回结果¶

    kernel[(num_programs, 1, 1)](y, x, x.stride(0), y.stride(0), n_rows, n_cols, BLOCK_SIZE, num_stages)
return y
    • kernel[(num_programs, 1, 1)]：使用动态计算出来的 num_programs 作为网格大小（Grid Size，X 维度为 num_programs），启动持久化（Persistent）内核。这些程序块会通过前面见过的 Grid-Stride Loop 自动瓜分并处理完所有的行，最后返回计算好的 Softmax 输出张量 y。

    5.3.6 实际调用¶

    kernel[(num_programs, 1, 1)](y, x, x.stride(0), y.stride(0), n_rows, n_cols, BLOCK_SIZE, num_stages)

    因为之前已经编译过了，我们也可以不用传入tl.constexpr的变量：

    kernel[(num_programs, 1, 1)](y, x, x.stride(0), y.stride(0), n_rows, n_cols)

    如果我们传入的被标记为 tl.constexpr（编译期常量，如 BLOCK_SIZE、num_stages 等）的参数发生修改，会产生以下核心影响：

    5.3.6.1. 触发重新编译（Recompilation / Cache Miss）¶

    tl.constexpr 不是普通的运行时变量。在 Triton 的 JIT 编译机制中，这些常量会直接参与 编译期的常量折叠、循环展开、静态内存分配以及硬件配置推导（例如决定 Shared Memory 的分配大小、线程块的网格排布等）。

    • 当你修改了 tl.constexpr 的值（例如把 BLOCK_SIZE 从 128 改为 256），原有的编译缓存不再适用。
    • Triton 会检测到参数变化，并 自动触发重新编译，生成一套全新的底层机器码（PTX / SASS）。
    5.3.6.2. 产生编译延迟（Latency Spike）¶
    • 在使用新常量值的 第一次调用时，程序会出现明显的停顿（卡顿），因为 Triton 需要重新走一遍 JIT 编译流程（包括 Python AST 解析、MLIR 转换、LLVM 优化和编译）。
    • 后续调用：只要 tl.constexpr 的值保持不变，Triton 就会命中缓存，直接执行已经编译好的内核，不会再有额外的编译开销。
    5.3.6.3. 缓存膨胀（Cache Bloat）¶

    Triton 会为每一组不同的 tl.constexpr 组合在内存中缓存一份独立的编译产物。如果你在代码中频繁动态改变这些常量（比如每次循环都传一个随机的 BLOCK_SIZE），会导致缓存中积压大量不同版本的内核，占用额外的内存。

    正因为 tl.constexpr 改变会引发重新编译，所以在实际工程中：

    • 应当保持其稳定性：不要在热路径（Hot Path）中随意动态改变 tl.constexpr 的值。
    • 它本质是编译期参数：虽然代码语法上像函数参数，但它的角色类似于 C++ 中的模板参数（Template Parameter）。

    6. 性能基准测试¶

    6.1 代码¶

    @triton.testing.perf_report(
    triton.testing.Benchmark(
        x_names=['N'],  # 用作图表 X 轴的参数名称
        x_vals=[128 * i for i in range(2, 100)],  # `x_name` 的不同可能取值
        line_arg='provider',  # 其值对应图表中不同折线的参数名称
        line_vals=['triton', 'torch', 'naive_softmax'],  # `line_arg` 的可能值
        line_names=["Triton", "Torch", "Naive Softmax"],  # 折线的标签名称
        styles=[('blue', '-'), ('green', '-'), ('red', '-')],  # 折线样式
        ylabel="GB/s",  # Y 轴的标签名称
        plot_name="softmax-performance",  # 图表名称。也用作保存图表的文件名。
        args={'M': 4096},  # 未包含在 `x_names` 和 `y_name` 中的函数参数值
    ))
def benchmark(M, N, provider):
    x = torch.randn(M, N, device=DEVICE, dtype=torch.float32)
    stream = getattr(torch, DEVICE.type).Stream()
    getattr(torch, DEVICE.type).set_stream(stream)
    if provider == 'torch':
        ms = triton.testing.do_bench(lambda: torch.softmax(x, axis=-1))
    if provider == 'triton':
        ms = triton.testing.do_bench(lambda: softmax(x))
    if provider == 'naive_softmax':
        ms = triton.testing.do_bench(lambda: naive_softmax(x))
    gbps = lambda ms: 2 * x.numel() * x.element_size() * 1e-9 / (ms * 1e-3)
    return gbps(ms)

    6.2 代码解释¶

    6.2.1 代码整体结构概述¶

    • @triton.testing.perf_report：这是 Triton 提供的一个装饰器，用来自动运行测试、收集性能数据，并最终可以将其绘制成美观的折线图。
    • Benchmark 配置：
    • x_names=['N']：以矩阵的列数 N 作为横轴（从 128 \times 2 一路测到 128 \times 99）。
    • line_arg='provider'：指定用哪个参数来分出三条不同的折线，对应的值是 ['triton', 'torch', 'naive_softmax']。
    • args={'M': 4096}：固定矩阵的行数 M = 4096。
    • benchmark 函数：核心测试逻辑。针对不同的 provider，调用对应的 softmax 实现，并利用 triton.testing.do_bench 测量执行时间，最后换算成显存带宽（GB/s）返回。

    6.2.2 关于 stream 的代码¶

    在 benchmark 函数内部有这样三行代码：

    stream = getattr(torch, DEVICE.type).Stream()
getattr(torch, DEVICE.type).set_stream(stream)

    这几行代码的核心目的是：在测试某个算子的性能之前，为当前的 PyTorch/CUDA 执行流（Stream）创建一个独立的、干净的测试流，并将其设为当前设备的默认当前流。

    6.2.2.1 为什么在 Benchmark 中必须这样做？¶
    1. GPU 异步执行特性： GPU 上的所有操作（如 PyTorch 的张量计算、Triton Kernel 启动）默认都是异步（Asynchronous）的。当你在 Python 里调用 torch.softmax(x) 时，CPU 只是把任务“扔”给了 GPU 的命令队列（Stream），然后就立刻返回了，并不代表 GPU 已经算完了。
    2. 避免与其他任务或默认流冲突： 如果直接用 PyTorch 的默认流（Default Stream），在这个测试运行之前，GPU 可能还在排队执行其他杂七杂八的初始化或内存分配操作。这会导致 triton.testing.do_bench 测出来的时间不准（包含了排队等待的时间）。
    3. do_bench 的准确测量依赖显式同步：
      • triton.testing.do_bench 会对传入的 lambda 函数进行反复多次的热身（Warmup）和正式计时（Timing）。
      • 为了确保计时精确，它需要在每次 Kernel 执行前后准确地同步。
      • 通过显式创建一个干净的 stream 并 set_stream，可以确保测试代码运行在一个完全隔离的执行队列里，排除外部事件的干扰。
    6.2.2.2 这几行代码的字面含义拆解：¶
    • DEVICE.type：通常是字符串 "cuda"（或 "hip" 等）。
    • getattr(torch, DEVICE.type).Stream()：动态获取对应硬件的 Stream 类（如 torch.cuda.Stream()），并在当前 GPU 设备上创建一个新的专属流。
    • getattr(torch, DEVICE.type).set_stream(stream)：将这个新创建的流设置为当前线程的当前活动流（Current Stream）。接下来无论是 PyTorch 算子还是 Triton 算子，都会自动提交到这个干净的流中执行，保证了 Benchmark 数据的纯净和公平。

    6.2.3 为什么之前的脚本没有用stream？¶

    6.2.3.1. 默认流（Default Stream / Stream 0）的存在¶

    在 PyTorch 和 CUDA 中，如果你不显式创建和切换 Stream，所有的操作（包括张量分配、PyTorch 算子、Triton Kernel 启动）都会自动提交到当前设备的 默认流（通常也就是 Stream 0）中。

    • 对于普通的前向/反向功能测试、Debug 脚本：你的目的只是验证代码逻辑对不对、数值算得准不准（比如用 torch.allclose 对比），顺序执行即可，完全不需要关心微秒级的计时误差，因此用默认流完全够用。
    6.2.3.2. 为什么在 perf_report（Benchmark）里最好显式隔离 Stream？¶

    triton.testing.perf_report 是专门用来做 极致性能压测 的工具。在做 Benchmark 时，微小的环境干扰都会影响测量结果：

    • 消除外部干扰：如果你不给 Benchmark 创建一个干净的专属 Stream，它就会混在 PyTorch 进程默认的全局队列里。如果在测试运行前刚好有一些后台内存分配或上一个测试的残留任务在默认流排队，Benchmark 测出来的时间就会把这些“排队等待的时间”错误地计算进去，导致测得的显存带宽（GB/s）偏低或不稳定。
    • do_bench 的精确计时要求：Triton 的 do_bench 工具内部会进行非常严格的 cudaEvent 计时和热身。为了保证测试结果具备工业级的参考价值（可以用来发论文或对比优化效果），必须保证测试环境是一个纯净、隔离的执行队列。

    7. Triton和CUDA代码对比¶

    7.1 Triton设置启动网格和块大小与常规CUDA程序的区别¶

    通过这个例子我们可以比较triton和一般cuda程序设置线程(block和grid)的区别：triton是根据硬件限制，启动足够的程序(对应CUDA程序的块)和线程把sm占满，如果输入/输出数据量大于线程数，就用跨步循环。而CUDA程序通常设置线程数等于输入/输出数据量 ，让通过大量线程把sm占满，甚至超过gpu可以支持的量。

    维度 Triton 的硬件受限调度模型 (Bounded & Persistent) 传统 CUDA 的数据驱动模型 (Over-subscribed / 1:1)
    网格大小决定因素 硬件物理上限（\text{SM} \times \text{Occupancy}）与问题规模的较小值。 数据集大小（例如每一行或每个元素对应一个线程/块）。
    线程与数据关系 少数持久化程序通过 跨步循环 (Grid-Stride Loop) 轮流处理所有数据。 大量线程/块直接对齐数据，通常呈现“一个线程/块处理一个或多个固定数据”的映射。
    硬件调度方式 类似软件层的 Worker Pool（线程池），每个 SM 分配固定数量的持久任务。 依靠 GPU 硬件调度器管理庞大的 Block 队列，排队执行。

    7.1.1 Triton 的硬件受限调度模型分析¶

    这种模型将线程分配的控制权从“数据规模”转移到了“硬件物理极限”上。

    • 优势：
      • 极低的调度开销：当处理含有数百万行的矩阵时，如果采用传统 CUDA 启动数百万个 Block，GPU 的硬件调度器会陷入繁重的任务分发和上下文切换中。Triton 只启动刚好填满所有 SM 的程序块（例如几十个或几百个），避免了调度队列拥堵。
      • 资源可控与高 Occupancy：通过编译器静态分析寄存器（n_regs）和共享内存（size_smem），它能精确计算出怎样才能让每个 SM 达到最高并发度，防止因资源超额分配导致性能暴跌。
      • 缓存局部性更好：由于持久化程序会连续处理多行数据，L2 缓存的命中率往往更高。
    • 劣势：
      • 编程思维转变：开发者不能再简单地写 int idx = blockIdx.x 就万事大吉，必须在内核中显式编写循环（如 for row_idx in tl.range(...)），这要求对任务切分有更清醒的认知。

    7.1.2 传统 CUDA 的数据驱动模型分析¶

    这种模型直观地将问题空间映射到硬件执行空间，是 GPU 编程教学和早期优化的主流范式。

    • 优势：
      • 直观易懂：思维模型极度简单。如果要处理 100 万个元素，就直觉地启动 100 万个线程或对应的 Block。索引计算通常只需一行代码（int tid = blockIdx.x * blockDim.x + threadIdx.x;）。
      • 硬件容错与弹性：GPU 硬件架构本身针对“海量线程”进行了深度优化，硬件调度器能够自动把超量的 Block 排队并调度到空闲的 SM 上，开发者无需手动编写循环去“平衡”负载。
    • 劣势：
      • 过量启动的隐患：如果盲目启动远超硬件承载能力的 Block 数量，硬件调度器会产生额外的管理开销。虽然现代 GPU 调度器对此做了优化，但在极端情况下仍会拖慢启动阶段的效率。
      • 资源分配被动：传统 CUDA 中如果每个线程/块消耗的寄存器过多，直接会导致硬件无法高并发运行（Occupancy 骤降），而这种崩溃往往在运行时才通过性能下降暴露，缺乏编译期的强力自动化推导与干预。

    现代高性能 GPU 编程（无论是 Triton 还是手写高级 CUDA）正在越来越多地向 Triton 这种“根据硬件算力定网格，利用循环消化数据”的模式靠拢。它将硬件资源利用率的主动权交给了编译器，从而在绝大多数场景下帮开发者避开了因线程超载或资源争抢导致的性能陷阱。

    7.2 Triton与CUDA编程思维的本质区别¶

    CUDA与Triton 的本质区别，绝不仅仅是“C++/CUDA 语法 vs Python 语法”这种表面形态的差异，而是 软件对硬件抽象层级（Abstraction Layer）的颠覆性重构。

    7.2.1 核心视角的根本转换：Thread-Centric vs. Block-Centric¶

    7.2.1.1. CUDA：“把程序员当成硬件调度器”（Thread-Centric，单线程视角）¶

    在 CUDA 编程中，你的核心任务是 编写单个线程（Thread）的代码，然后由硬件的硬件调度器把成千上万个这样的线程分发到不同的Streaming Multiprocessor(SM)上执行。

    • 你必须显式计算身份：写每一行 CUDA 代码时，脑子里都必须有 threadIdx.x、blockIdx.x、blockDim.x 组成的坐标系。你需要通过这些内置变量去计算“我是哪个线程，我该处理哪个全局内存地址”。
    • 代码写的是“个体”：你的代码描述的是“第 i 个线程要做什么”。如果一个数组有 1000 个元素，启动了 1000 个线程，那么代码中的 A[tid] 就是第 tid 个线程去访问第 tid 个数据。
    7.2.2.2. Triton：“把编译器当成硬件调度器”（Block-Centric / Program-Centric，块级向量视角）¶

    在 Triton 中，你的视角被拔高到了整个程序块（Program / Block，对应 CUDA 的 Thread Block）层面。

    • 你不再关心单个线程：在 Triton 的代码里，你根本找不到 threadIdx 或任何线程索引。你操作的对象直接就是 张量（Tensor / Vector Register）。例如，row = tl.load(...) 加载进来的是一整行数据，row - tl.max(row) 是对一整行向量做并行减法。
    • 代码写的是“整体”：你的代码描述的是“整个程序块如何协作处理这一大块数据（如一整行）”。具体的线程怎么分工、数据怎么在 32 个线程之间倒腾，全部由 Triton 编译器在后台自动化搞定。

    7.2.2 内存与数据流模型的差异：显式搬运 vs. 声明式数据流¶

    7.2.2.1. CUDA 的内存模型：手动的“搬砖”艺术¶

    在 CUDA 中，管理数据在 Global Memory（DRAM）、Shared Memory（SRAM）和 Registers 之间的流转，是程序员的核心工作量：

    • 必须显式写出 __shared__ float s_buf[256];。
    • 必须手写协作加载逻辑：让不同的线程把数据从全局内存搬到共享内存中。
    • 搬完之后，必须显式调用 __syncthreads() 做块内同步，否则后面的代码读到的一定是脏数据。
    • 稍有不慎就会发生 数据竞态（Data Race） 或 Bank Conflict（共享内存体冲突）。
    7.2.2.2. Triton 的内存模型：现代编译器的“智能托管”¶

    在 Triton 中，内存层级（特别是 Shared Memory）对程序员是 基本透明 的：

    • 你通过 tl.load() 和 tl.store() 声明“我需要从全局内存加载这块数据到寄存器/块缓存中”。
    • Triton 编译器（基于 MLIR 框架）会进行极其复杂的静态分析， 自动决定 哪些数据应该缓存到 Shared Memory 中、怎么利用软件流水线（Software Pipelining）去掩盖全局内存访问延迟、如何优化内存合并访问（Memory Coalescing）。
    • 你不需要手动写 __syncthreads()，编译器会在生成的底层 PTX/SASS 代码中精确插入同步原语。

    7.2.3 算法复杂度的封装：手动实现规约树 vs. 高级算子直达¶

    7.2.3.1. CUDA：手写并行的“螺丝钉”¶

    假设你要做一个简单的求和规约（Reduction）：

    • 在 CUDA 里，你必须自己写一个 并行规约树（Parallel Reduction Tree）。
    • 你需要用到 Warp Shuffle 指令（如 __shfl_down_sync）在同一个 Warp 的 32 个线程间交换数据，然后用 Shared Memory 在不同 Warp 间交换数据。
    • 你要极其小心地处理线程束分化（Warp Divergence）和数组越界，代码往往充满各种位运算和边界判断。
    7.2.3.2. Triton：高级数学语义的直白表达¶

    在 Triton 中，规约、广播、矩阵乘法（通过 tl.dot）都是 一等公民（First-Class Citizens）：

    • 你只需要写下 tl.sum(tensor, axis=0) 或 tl.max(tensor, axis=0)。
    • Triton 编译器知道当前硬件的目标架构（比如 Ampere 的 Tensor Core 或者是 Hopper 的 TMA / WGMMA 单元），它会把这个高级的 tl.sum 自动编译成当前硬件上最高效的机器指令序列。

    7.2.4 核心对比总结表¶

    维度 CUDA 编程思维 (Thread-Centric) Triton 编程思维 (Block-Centric)
    控制粒度 微观：精确到每一个硬件线程（Thread）的执行路径。 宏观：关注一个任务块（Program/Block）的高级数据流。
    坐标系 必须硬编码 threadIdx、blockIdx、gridDim。 使用逻辑坐标和向量化/矩阵化的 Tensor 形状。
    同步与通信 程序员手动管理：__syncthreads()、__shfl_sync 等。 编译器自动管理：隐式同步，消除绝大部分手动死锁风险。
    SRAM/Shared Mem 程序员显式声明、分配、索引并管理生命周期。 编译器自动优化调度，开发者主要操作逻辑 Tensor。
    心智负担 极高：需兼顾算法数学逻辑与底层硬件指令调度（寄存器压力、Bank Conflict）。 较低：专注于算法的数据依赖和张量变换，类似写高性能 Python/NumPy。
    跨架构移植性 较低：底层架构变动（如从 Volta 到 Hopper）往往需要重写算子以适配新指令。 较高：由 Triton 编译器后端负责将高级 IR 翻译并适配不同的 GPU 架构。

    7.2.5 总结¶

    如果把写 CUDA 比作“用汇编语言手写操作系统内核”，每一个寄存器和同步点都要亲自把关，极具挑战但上限极高； 那么写 Triton 就是 “用高级系统语言（如 Rust/C++）写并发程序”，你把控的是程序的整体架构和数据流，而把复杂的底层寄存器分配、线程同步、硬件指令排布交给了功能强大的现代编译器。这也正是为什么近几年大模型基础设施（如 FlashAttention、vLLM 的自定义核）越来越多地转向 Triton 的根本原因——研发效率与极致性能实现了前所未有的平衡。

    7.3. Triton 如何自动处理规约（Reduce）操作？¶

    当你写下：

    row = tl.load(input_ptrs, mask=mask, other=-float('inf'))
...
denominator = tl.sum(numerator, axis=0)

    你并没有写任何循环或线程同步代码，但 Triton 编译器在底层帮你完成了以下复杂的协作流程：

    1. 分布式数据加载 (tl.load)： input_ptrs 是一个包含整个 BLOCK_SIZE（例如 1024 个元素）的指针向量。当执行 tl.load 时，Triton 编译器会把这 1024 个元素的加载任务 自动分发 给该 Block 内的所有线程（由 num_warps 决定总线程数，如 8 个 warp 共 256 个线程）。每个线程并行加载其中的一小部分（例如每个线程连续或交叉加载 4 个元素），并存入各自的寄存器中。
    2. 块内规约 (tl.sum / tl.max)： 当执行 tl.sum(numerator, axis=0) 时，由于这 1024 个元素分布在 256 个线程的私有寄存器中，Triton 编译器会自动在底层生成高效的 Warp-level Reduce（束内规约，使用 shfl 指令） 和 Block-level Reduce（块内规约，利用共享内存 Shared Memory） 代码：
      • 首先，同一个 Warp 内的 32 个线程通过寄存器洗牌指令（Shuffle）在极短时钟周期内求出各自 Warp 的局部和。
      • 接着，各个 Warp 之间通过 Shared Memory 进行跨 Warp 的聚合，最终将 1024 个元素的总和规约出一个标量结果，并广播或分发给需要的线程。

    7.4. 如果自己用 CUDA 实现，你需要做什么？¶

    如果用原生 CUDA 实现这个 Softmax 逻辑，你将不得不手动处理 Triton 替你屏蔽掉的所有底层痛点：

    1. 显式线程索引计算： 必须手写 int tid = threadIdx.x + blockIdx.x * blockDim.x;，并处理由于 n_cols 不是线程块大小整数倍时的 越界保护。
    2. 手写 Shared Memory Tiling 与同步： 若要计算 tl.max 和 tl.sum，你需要声明动态或静态共享内存 __shared__ float s_data[];。把全局内存（DRAM）的数据协作加载到共享内存中，并在关键位置手动插入 __syncthreads() 防止数据竞态（Data Race）。
    3. 手写规约算法（Reduction Tree）： 必须用 C++ / CUDA 实现高效的树形规约（Parallel Reduction）或利用 Warp Primitive（如 __shfl_xor_sync）逐级累加，处理奇偶对齐、线程束分化（Warp Divergence）等硬件陷阱，代码量通常会膨胀数倍。

    Triton 的核心魔力在于它把“硬件的并行调度（线程分配、寄存器分配、Shared Memory 缓存、Warp 级协作）”交给了编译器去自动化求解，而让开发者专注于“算法的数据流逻辑（矩阵乘、Softmax、LayerNorm 的数学表达）”，这也是为什么它能用极短的代码写出接近甚至达到手写 CUDA 高度优化水平的核心原因。

    7.5 如何知道 Triton 消耗了多少寄存器和共享内存？¶

    在 Triton 中，我们可以直接通过被 warmup 或执行后的 kernel 对象获取这些硬件资源指标：

    kernel = softmax_kernel.warmup(y, x, x.stride(0), y.stride(0), n_rows, n_cols, 
                               BLOCK_SIZE=BLOCK_SIZE, num_stages=num_stages, num_warps=num_warps, grid=(1, ))

n_regs = kernel.n_regs          # 每个线程使用的通用寄存器数量 (Registers per thread)
size_smem = kernel.metadata.shared  # 该 Block 静态申请的共享内存大小 (Bytes)
    • n_regs：由 NVIDIA 的 PTXAS 编译器在后端统计。它直接决定了每个 SM 能同时运行多少个 Block（即硬件占用率 Occupancy）。如果 n_regs 太高，寄存器溢出（Spill）到本地内存（Local Memory / DRAM），性能就会暴跌。
    • size_smem：由于设置了 num_stages = 4（软件流水线），编译器会利用 Shared Memory 做多缓冲（Multi-buffering）来掩盖访存延迟，这里的 size_smem 就是为此分配的静态共享内存大小。

    7.6 Triton 是怎么实现的？¶

    Triton 的核心编译流程经历了以下步骤：

    1. Triton-IR / TTGIR（块级中间表示）：你的 Python 代码首先被转成 MLIR 的高级方言，保留了 tensor<BLOCK_SIZExf32> 这种块级语义。
    2. Layout Conversion（布局转换与线程映射）：编译器根据你指定的 num_warps = 8（共 256 个线程），自动把一维的 BLOCK_SIZE（例如 1024 个元素）切分并分发（Distribute）到 256 个线程的私有寄存器中。每个线程分到 4 个连续或交叉的元素（称为 寄存器切片 Register Slicing）。
    3. LLVM-IR 与 PTX 生成：
      • 遇到 tl.max 和 tl.sum 时，编译器自动展开成目标架构的 Warp Shuffle 指令（如 shfl.down）。
      • 遇到多阶段流水线（num_stages=4）时，编译器自动插入异步拷贝指令（如 cp.async，如果是 Hopper 还会用到 TMA），实现 计算与全局内存加载的重叠（Overlap）。

    7.7 等价的CUDA代码实现¶

    为了直观理解 Triton 背后替你干了多少苦力活，下面将上述 Triton 的 Softmax 核心逻辑手写成 等价的、结构清晰的 CUDA C++ 代码：

    template <int BLOCK_SIZE, int THREADS_PER_BLOCK>
__global__ void softmax_kernel_cuda(
    float* __restrict__ output_ptr,
    const float* __restrict__ input_ptr,
    long input_row_stride,
    long output_row_stride,
    int n_rows,
    int n_cols
) {
    constexpr int kItemsPerThread = BLOCK_SIZE / THREADS_PER_BLOCK;
    static_assert(BLOCK_SIZE % THREADS_PER_BLOCK == 0, "BLOCK_SIZE must be divisible by THREADS_PER_BLOCK");

    extern __shared__ float shared_memory[];

    int row_start = blockIdx.x;
    int row_step = gridDim.x;
    constexpr int num_warps = THREADS_PER_BLOCK / 32;

    for (int row_idx = row_start; row_idx < n_rows; row_idx += row_step) {
        const float* row_input = input_ptr + row_idx * input_row_stride;
        float* row_output = output_ptr + row_idx * output_row_stride;

        int tid = threadIdx.x;
        int warp_id = tid / 32;
        int lane_id = tid % 32;

        // 1. 并行加载数据到寄存器数组
        float local_vals[kItemsPerThread];
        #pragma unroll
        for (int i = 0; i < kItemsPerThread; ++i) {
            int col_idx = tid + i * THREADS_PER_BLOCK;
            if (col_idx < n_cols) {
                local_vals[i] = row_input[col_idx];
            } else {
                local_vals[i] = -FLT_MAX;
            }
        }

        // 2. 求最大值
        float thread_max = -FLT_MAX;
        #pragma unroll
        for (int i = 0; i < kItemsPerThread; ++i) {
            thread_max = fmaxf(thread_max, local_vals[i]);
        }

        // Warp 内规约
        for (int offset = 16; offset > 0; offset /= 2) {
            thread_max = fmaxf(thread_max, __shfl_down_sync(0xffffffff, thread_max, offset));
        }

        if (lane_id == 0) {
            shared_memory[warp_id] = thread_max;
        }
        __syncthreads();

        // 跨 Warp 汇总最大值并广播
        float block_max = -FLT_MAX;
        if (warp_id == 0) {
            if (tid < num_warps) {
                block_max = shared_memory[tid];
            }
            for (int offset = num_warps / 2; offset > 0; offset /= 2) {
                block_max = fmaxf(block_max, __shfl_down_sync(0xffffffff, block_max, offset));
            }
            if (lane_id == 0) {
                shared_memory[0] = block_max;
            }
        }
        __syncthreads();
        block_max = shared_memory[0]; // 安全广播给所有线程

        // 3. 减去最大值并求指数和
        float local_sum = 0.0f;
        #pragma unroll
        for (int i = 0; i < kItemsPerThread; ++i) {
            int col_idx = tid + i * THREADS_PER_BLOCK;
            if (col_idx < n_cols) {
                local_vals[i] = __expf(local_vals[i] - block_max);
                local_sum += local_vals[i];
            } else {
                local_vals[i] = 0.0f;
            }
        }

        // Warp 内求和规约
        for (int offset = 16; offset > 0; offset /= 2) {
            local_sum += __shfl_down_sync(0xffffffff, local_sum, offset);
        }

        if (lane_id == 0) {
            shared_memory[warp_id] = local_sum;
        }
        __syncthreads();

        // 跨 Warp 汇总总和并广播
        float block_sum = 0.0f;
        if (warp_id == 0) {
            if (tid < num_warps) {
                block_sum = shared_memory[tid];
            }
            for (int offset = num_warps / 2; offset > 0; offset /= 2) {
                block_sum += __shfl_down_sync(0xffffffff, block_sum, offset);
            }
            if (lane_id == 0) {
                shared_memory[0] = block_sum;
            }
        }
        __syncthreads();
        block_sum = shared_memory[0]; // 安全广播给所有线程

        // 4. 归一化并写回
        #pragma unroll
        for (int i = 0; i < kItemsPerThread; ++i) {
            int col_idx = tid + i * THREADS_PER_BLOCK;
            if (col_idx < n_cols) {
                row_output[col_idx] = local_vals[i] / block_sum;
            }
        }
    }
}

    这里不解释上面的代码，只是让同学们看一下如果自己手写需要的代码量。

    7.8 总结对比¶

    如果在纯 CUDA 中实现上述功能，我们必须亲自动手写：

    1. 多级规约树（Warp 内用 __shfl_down_sync，Warp 间用 __shared__ 缓存）。
    2. 同步屏障（到处插入 __syncthreads() 防止读写冲突）。
    3. 寄存器切片分配（手算每个线程分几个数据，处理边界掩码）。

    而在 Triton 中，我们只需要写那几行简洁的 tl.load、tl.max、tl.sum 和矩阵/向量运算，上面这几百行繁琐且容易出错的底层 CUDA 模板代码，全部由 Triton 编译器在幕后自动为你生成。

    8. CUDA软件流水线(拓展知识)¶

    8.1 硬件流水线和软件流水线¶

    在 CUDA 和 GPU 架构中，硬件流水线（Hardware Pipeline） 和 软件流水线（Software Pipeline） 是两个不同层面的概念，但它们的核心目的都是 隐藏延迟、提升吞吐量。

    8.1.1. 硬件流水线（Hardware Pipeline）¶

    定义： 硬件流水线是 芯片电路设计层面的概念。GPU 的计算单元和指令执行单元被设计成多级流水线结构，就像工厂的流水线装配线一样，将一个复杂的指令或操作拆解为多个连续的阶段（Stage），由不同的硬件电路负责。

    在 CUDA / GPU 中的体现：

    • 指令流水线：GPU 执行一条指令通常需要经过发射（Issue）、解码（Decode）、执行（Execute）、写回（Writeback）等多个硬件时钟周期阶段。
    • 功能单元流水线：GPU 内部的各类算术逻辑单元（如 FP32 ALU、Tensor Core、SFU 特殊函数单元、LD/ST 访存单元）本身都是流水线化的。前一个指令的数据还在单元里计算时，后一个指令就可以进入该单元。
    • Warp 调度与硬件多线程：GPU 通过硬件级的 Warp 调度器（Warp Scheduler）在几十个 Warp 之间进行零开销切换。当一个 Warp 因为等待内存数据（Latency）而停顿（Stall）时，硬件流水线立刻切换到另一个准备好的 Warp 执行指令，以此来掩盖硬件延迟。

    8.1.2. 软件流水线（Software Pipeline）¶

    定义： 软件流水线是 编译器优化或程序员手写代码层面的技术（在写 CUDA C++ 或 Triton 时极常用）。它是针对循环（Loop）的一种高级优化手段：将循环的不同迭代（Iterations）中的操作重叠执行，让数据的“加载”和“计算”交织在一起。

    为什么 CUDA 极其需要软件流水线？ GPU 面临的最大瓶颈是 Memory Wall（访存延迟）。从全局内存（Global Memory / DRAM）读取数据到寄存器或共享内存（SRAM）需要数百个时钟周期。如果在循环中采用“先读完所有数据，再开始计算”的串行模式，计算单元（ALU/Tensor Core）大部分时间都会处于饥饿状态。

    软件流水线的经典实现（以 CUDA 的异步拷贝 + 多缓冲为例）： 假设我们要循环处理 10 个数据块（Block 0 到 9）：

    1. 未优化的串行循环：

      • 循环 0：从全局内存加载数据 0 \rightarrow 计算数据 0（CPU/GPU 干等加载完成）。
      • 循环 1：从全局内存加载数据 1 \rightarrow 计算数据 1……

    2. 软件流水线（Pipeline / Double Buffering）：

      • 预热（Prologue）：在循环开始前，先把“数据 0”异步加载到共享内存中。
      • 正式循环（Loop）：
        • 计算 当前循环的块（例如正在用 SRAM 里的 数据 i 进行 Tensor Core 计算）。
        • 同时，利用硬件的异步拷贝指令（如 CUDA 的 cp.async），在后台把下一个循环的 数据 i+1 从全局内存加载到共享内存中。
    • 这样，计算第 i 块的时间，正好用来加载第 i+1 块的数据，完美掩盖了访存延迟。

    8.1.3. 两者的核心区别与联系¶

    维度 硬件流水线 (Hardware Pipeline) 软件流水线 (Software Pipeline)

    作用层级 指令级 / 运算单元级（微观） 循环级 / 算法逻辑级（宏观）
    解决的问题 提高单个指令的吞吐率、实现多线程零开销切换 掩盖访存延迟（Memory Latency）、实现算力压榨

    联系： 软件流水线是建立在硬件流水线和异步硬件特性（如异步访存指令、共享内存）基础之上的上层策略。程序员通过编写“软件流水线”代码，把任务合理分批并错开，从而最大化地喂饱下层的“硬件流水线”。

    8.2 软件流式线和CUDA Stream¶

    在 CUDA 编程中，软件流水线（Software Pipeline） 和 CUDA Stream（流） 都是用来实现并行和掩盖延迟（Latency Hiding）的核心技术，但它们工作在 完全不同的抽象层级。两者既有明确的分工，又可以完美配合。

    8.2.1. 核心维度的区别¶

    维度 CUDA Stream (流) 软件流水线 (Software Pipeline)
    抽象层级 Host 端 / 任务调度层（宏观、任务级） Device 端 / Kernel 内部层（微观、指令/循环级）
    主要目的 异步并发执行不同的任务（如：重叠 CPU/GPU 传输与计算、多 Kernel 并发） 在一个 Kernel 内部，将“数据加载”与“矩阵计算”交织重叠，掩盖访存延迟
    作用域 跨多个 Host API 调用或多个 Kernel 单个 Kernel 内部的 for 循环

    8.2.2. 它们是如何协同工作的？¶

    虽然层级不同，但在高性能 CUDA 程序中，CUDA Stream 和软件流水线通常是组合使用的，它们构成了两级流水线：

    • 宏观层面（CUDA Stream 级）： 你通过不同的 Stream，让 GPU 在执行第 N 个 Batch 的 Kernel 计算的同时，通过另一个 Stream 异步把第 N+1 个 Batch 的数据从 CPU 内存（Host）拷到 GPU 显存（Device）。
    • 微观层面（Software Pipeline 级）： 当第 N 个 Batch 的 Kernel 正在 GPU 内部执行时，Kernel 内部的代码通过软件流水线（如 cp.async 和多缓冲），在计算当前 Tile 的同时，把下一个 Tile 从全局显存（Global Memory）加载到共享内存（Shared Memory）中。

    简单来说：Stream 负责把大任务像传送带一样连续送进 GPU，而软件流水线负责在 GPU 内部把细分的小数据块无缝衔接好。

    8.2.3. 一个典型的结合场景（以大模型推理/训练为例）¶

    假设你在编写一个高性能的 Transformer 算子或 vLLM 服务：

    1. Stream 负责并发：

      • 主 Stream 运行大矩阵乘法（GEMM）Kernel。
      • 另一个 Stream 同时处理下一个 Token 的 Host-to-Device 内存拷贝。

    2. 软件流水线负责加速 Kernel：

      • 在那个运行矩阵乘法的 Kernel 内部，利用软件流水线（Software Pipelining）技术，让 SM 中的 Tensor Core 在做乘加运算时，计算单元周围的 LD/ST 单元正在异步搬运下一块数据。

    两者的协同最终实现了软硬件资源的最大化利用，让 GPU 算力不因“等数据”而闲置。

    8.3 fake_software_pipeline.cu¶

    在看真正的软件流水线代码之前，我们来看一看“逻辑”上的软件流水线代码。完整代码在cuda-stream/fake_software_pipeline.cu。

    // 假的块级双缓冲软件流水线内核
__global__ void fake_pipeline_kernel(const float* __restrict__ g_in, 
                                     float* __restrict__ g_out, 
                                     int n_elements,
                                     int elements_per_block) {
    // 每个 Block 负责处理一段较大的数据（elements_per_block）
    // 该段数据被划分为多个 Tile，每个 Tile 的大小等于线程块大小 (blockDim.x = 1024)
    __shared__ float smem[2][BLOCK_SIZE];

    int tid = threadIdx.x;
    int block_start_idx = blockIdx.x * elements_per_block;
    int num_tiles = elements_per_block / blockDim.x;

    if (block_start_idx >= n_elements) return;

    // --- 阶段 1：预加载（Prologue）---
    // 在进入流水线循环前，先把第 0 个 Tile 加载到缓冲区 0 中
    int global_init_idx = block_start_idx + tid;
    if (global_init_idx < n_elements) {
        smem[0][tid] = g_in[global_init_idx];
    } else {
        smem[0][tid] = 0.0f;
    }
    __syncthreads(); // 等待初始数据加载完毕

    // --- 阶段 2：流水线主循环 ---
    for (int t = 0; t < num_tiles; ++t) {
        int cur_buf = t % 2;
        int next_buf = 1 - cur_buf;

        // 计算下一个 Tile 在全局内存中的起始位置
        int next_tile_idx = block_start_idx + (t + 1) * blockDim.x + tid;

        // 1. 异步/提前加载下一个 Tile 到另一块 Shared Memory 中（重叠访存）
        if (t + 1 < num_tiles && next_tile_idx < n_elements) {
            smem[next_buf][tid] = g_in[next_tile_idx];
        } else if (t + 1 < num_tiles) {
            smem[next_buf][tid] = 0.0f;
        }

        // 2. 对当前缓冲区中的数据进行计算（这里以乘 2 为例）
        float val = 0.0f;
        int cur_tile_idx = block_start_idx + t * blockDim.x + tid;
        if (cur_tile_idx < n_elements) {
            val = smem[cur_buf][tid] * 2.0f; 
        }

        // 3. 将当前计算结果写回全局内存 (DRAM)
        if (cur_tile_idx < n_elements) {
            g_out[cur_tile_idx] = val;
        }

        // 4. 线程同步：确保当前缓冲区的计算已完成、下一缓冲区的加载已发出
        __syncthreads();
    }
}

    上面的代码实现了一个典型的块级双缓冲软件流水线（Block-level Double-Buffered Software Pipeline）内核。它的核心目的是通过 用计算掩盖访存延迟（Latency Hiding），解决 GPU 编程中常见的访存受限（Memory-bound）瓶颈。

    8.3.1. 核心核心设计：双缓冲（Double Buffering）¶

    __shared__ float smem[2][BLOCK_SIZE];
    • 双缓冲区：共享内存（Shared Memory）被声明为大小为 2 的数组 smem[2][BLOCK_SIZE]。
    • 交替轮转：在循环中通过 cur_buf = t % 2 和 next_buf = 1 - cur_buf 实现缓冲区索引的实时切换。一个缓冲区用于 当前周期的计算与写回，另一个缓冲区用于 后台提前加载下一轮的数据。

    8.3.2. 执行流程拆解¶

    8.3.2.1 阶段 1：预加载（Prologue）¶
    int global_init_idx = block_start_idx + tid;

    smem[0][tid] = g_in[global_init_idx];
} else {
    smem[0][tid] = 0.0f;

    • __syncthreads() 确保所有线程都加载完毕后，循环才能安全开始，防止后续读取时数据未就位。
    8.3.2. 阶段 2：流水线主循环（Pipeline Loop）¶

    循环内部通过 4 个步骤实现了重叠执行：

    1. 异步/提前加载（Prefetch）： 
      if (t + 1 < num_tiles && next_tile_idx < n_elements) {
    smem[next_buf][tid] = g_in[next_tile_idx];
}

    当 GPU 正在处理当前 Tile（在 cur_buf 中）时，利用全局内存的访存带宽，把 下一个 Tile (t+1) 提前拉取到另一块共享内存 next_buf 中。

    1. 计算（Compute）：
    float val = smem[cur_buf][tid] * 2.0f;

    计算单元（ALU）对当前缓冲区 cur_buf 中的数据进行处理（示例中为简单的乘 2）。

    1. 写回（Store）：

    g_out[cur_tile_idx] = val;
    将计算结果写回全局内存。

    1. 同步屏障（Synchronization）：
    __syncthreads();

    这是该模式中最关键的一行。它有两个作用： * 防过早覆盖：确保所有线程都已经读完了 cur_buf 的数据，下一轮迭代才能把新数据写进这个缓冲区。 * 防提前读取：确保所有线程都已经把 next_buf 的加载请求发完并写入完毕，下一轮迭代才能去安全地读取它。

    8.3.3 问题¶

    这段代码虽然结构上具备双缓冲的 逻辑，但在真实的 GPU 硬件执行层面，它无法真正实现流水线（Pipeline）与访存掩盖。

    在上面的代码中， smem[next_buf][tid] = g_in[next_tile_idx]），数据的加载是通过通用计算/访存流水线发起的同步操作。线程必须“站在这里”等待数据从全局内存（DRAM）搬到寄存器再写入共享内存（SRAM），这无法脱离核心的阻塞等待。

    为了解决这个问题，在 Ampere 架构（如 RTX 3090、A100）及更新的 GPU 中，引入了 cp.async（异步拷贝指令）。它允许数据绕过寄存器，直接从全球内存（Global Memory）异步拷贝到共享内存（Shared Memory），由 GPU 专门的硬件搬运单元（Async Copy Engine）在后台执行。

    这样，计算单元（Tensor Core / ALU）在算当前块的时候，硬件后台在默默搬运下一个块，两者真正做到了硬件级的并行重叠。

    8.4.1.2.3 volatile 关键字¶

    告诉编译器：不要对这段汇编代码进行任何优化、重命名或删除。因为这是一个具有硬件副作用的异步操作，编译器如果用常规逻辑去“优化”它，会导致硬件指令错乱。

    8.4.1.2.4 PTX 指令字符串：cp.async.ca.shared.global [%0], [%1], 4;\n¶

    这是 Ampere 架构（RTX 30系、A100）及更新显卡引入的硬件指令：

    • cp.async：代表“异步拷贝”。它的意思是：“线程发出这个指令后，立刻就可以去干别的，底层的 Tensor Core / 拷贝单元会在后台默默把数据从显存搬到共享内存，不需要线程傻傻站着等。”
    • .ca：全称 Cache-All（缓存策略提示）。表示这次全局内存读取会尽量利用 L2 缓存。
    • .shared.global：指明数据流向——目标 在共享内存（Shared），源 在全局内存（Global）。
    • [%0] 与 [%1]：占位符，分别对应后面的输入操作数列表中的第 0 个和第 1 个变量。
    • 4：拷贝的字节数（sizeof(float) 等于 4 字节）。意味着每个线程单次异步搬运一个单精度浮点数。
    8.4.1.2.5 输入操作数映射：: : "r"(smem_addr), "l"(global_addr)¶

    这部分负责把 C++ 的变量桥接到汇编的占位符中：

    • "r"(smem_addr)：将 32 位的共享内存地址 smem_addr 放入一个通用的 32 位寄存器（对应汇编中的 %0）。
    • "l"(global_addr)：将 64 位的全局内存地址 global_addr 放入一个 64 位长整型寄存器（对应汇编中的 %1，在 PTX 中用 l 表示 64-bit integer）。

    通过这种方式，硬件可以直接控制数据从 DRAM 经由高速缓存直达 Shared Memory，完全不占用寄存器文件（Register File）作为中转，从而节省了宝贵的寄存器资源并最大化了带宽。

      • 较晚发起的 Group 1 (T_1) 继续在后台飞，完全不需要停下来等它，实现了 访存重叠。
    • 第一次 __syncthreads()：虽然当前线程知道 Group 0 完了，但必须等 块内所有线程 都到达这里，确保整个线程块都能安全去读取 smem[0]。

    8.4.2.2.3. 第二次 __syncthreads();（防写后读 WAR 竞态）¶
    • 这是最精妙的一步！ 为什么需要第二个同步屏障？
      • 竞态场景：在同一个 Block 中，假如线程 A 执行速度极快，已经算完了 smem[0] 并冲到了步骤 4，准备向 smem[0] 写入 T_2 的新数据；而线程 B 比较慢，还在读取 smem[0] 计算 T_0。
      • 屏障作用：这第二个 __syncthreads() 强制要求：“所有线程必须都消费完 smem[cur_buf]，谁也不许提前去覆盖它！”彻底杜绝了 Shared Memory 的写后读（WAR）冲突。

    说明：我们这个例子比较简单，因为每个位置只加载和读取自己的数据，实际通常不是这样，所以要加同步。
